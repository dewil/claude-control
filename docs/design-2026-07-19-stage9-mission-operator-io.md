# Stage 9: операторский I/O с mission-сессией (сводка + комментарий)

Две фичи TG-бота для наблюдения за живой mission-сессией:

1. **Сводка по запросу** - кнопка в меню агента отдаёт сводку "что сейчас происходит".
2. **Комментарий через reply** - reply на сообщение агента вбрасывает текст оператора в его живую сессию.

Решения по объёму (dwl, 2026-07-19): этап 1 = **механическая сводка** (без рефлексии агента) + **очередь комментариев**. Осмысленное резюме (агент сам пишет и шлёт в TG) и outbox-примитив агент→TG - отдельный следующий этап.

## Контекст механики (см. stage4-event-spool + разбор кода)

Критично: два типа агентов несовместимы по каналам связи.

- **mission-агент** (напр. spamogon-fixes) - живая интерактивная claude-сессия в tmux, пишет `state.<gen>.json` (в т.ч. `status_line`), работает в worktree. **Инбокса/спула НЕТ.** Единственный вход в сессию - `tmux send-keys` в pane, и reconciler делает это только когда pane на idle-промпте (fingerprint-гейт, `claude-agent-reconciler:1054-1062`).
- **event-агент** - НЕ живая сессия, spool→inbox→headless `claude -p` на событие. Сюда идут `/task`/`spool-put`. Резюмировать "сессию" тут нечего (one-shot, пустой `run/`).

Обе фичи применимы **только к mission-агентам**. Существующий `/task` до них не доходит - это другой канал.

Обратный канал агент→человек сейчас: pull (`status_line` в `state.<gen>.json` → человек читает через `/agent`) и push инфры (`CLAUDE_AGENT_ALERT_CMD`=`claude-agent-tgbot send`). Санкционированного примитива "агент сам пишет свободный текст человеку" нет.

## Фича 1: механическая сводка (этап 1)

**Что:** в `menu_view("ag:<name>")` бота - кнопка **📋 Сводка** (callback `m:sum:<name>`). Бот сам собирает и показывает:

- из `control.json`: `desired`, `phase`, `claim`, `acceptance`, `attention`, `hold`, `iterations`, `started_at`;
- из `state.<gen>.json`: `status_line`, `agent_claim` (самоотчёт агента);
- из `events.jsonl`: хвост N последних событий (уже есть `events_tail`).

Формат - компактный HTML (`<pre>`), как статус. **Агента не трогаем** - чистое чтение файлов реестра, новой инфры на стороне агента нет (о согласованности поколений между файлами и redaction событий - см. правки adversarial-гейта ниже).

Отличие от нынешнего `/agent`: добавляется явная фаза/attention/итерации + чуть длиннее хвост событий, в один экран под кнопкой. По сути - переиспользование `run_cli(["status"])` + `events_tail` в отдельном пункте меню.

## Фича 2: комментарий оператора в сессию (этап 1)

**UX:** reply на статус/сводку агента в боте + текст → текст уходит в живую сессию этого агента как наставление оператора (AGENT.md уже предписывает: "входящие сообщения в сессию - наставления оператора, учитывай их", `claude-rc-agent:284`).

**Роутинг reply→агент (бот).** У бота нет состояния сессий. Варианты сопоставить reply с агентом:

- (A) хранить лёгкий map `message_id → agent` в файле (`~/.claude-control/tgbot.sent.json`, кольцо на ~200 записей), писать при отправке статус/сводка-сообщения;
- (B) парсить имя агента из текста процитированного сообщения.

Решение: **(A)** - надёжнее, не зависит от формата текста. Дедуп доставки - по `update_id`.

**Доставка в mission-сессию (новая инфра).** Нельзя слать send-keys вслепую: если pane занят прогоном, нажатия попадут в середину работы. Нужна **mission-очередь** с дисциплинированным сливом:

- каталог `~/.claude-control/agents/<name>/mission-inbox/` (файлы `msg-<seq>.json`: `{text, from, at, id}`), запись под flock (как spool);
- бот кладёт сообщение в очередь (новый subcommand `claude-agent-run mission-put <name> --json ...`, идемпотентность по `tg:<update_id>`);
- **reconciler на каждом проходе** для mission-агента с непустой очередью: если pane на idle-промпте (тот же fingerprint-гейт, что и старт-кик) → `send-keys` следующего сообщения, пометить доставленным; если busy → оставить в очереди (дренаж на следующем idle). По одному за проход, дедуп по `id`.

Так поведение агента уже задано (AGENT.md), строим только очередь + дренаж.

**Безопасность вброса:** текст оператора доставляется в pane как пользовательский ввод. Обрамлять префиксом-маркером ("[оператор]: ...") чтобы агент не спутал с системным. Текст - недоверенный ввод от владельца (whitelist), инъекция в свою же сессию - не угроза уровня чужого пользователя, но маркер обязателен для однозначности.

## Вне объёма этапа 1 (следующий этап)

- **Осмысленное резюме по запросу** (агент сам рефлексирует и пишет сводку) - требует: (а) типа сообщения "summarize now" в mission-очереди, (б) **outbox-примитива агент→TG** (санкционированный `claude-agent-tgbot notify` из сессии, сейчас не проложен; mission с `autonomy=act` имеет Bash, но путь не узаконен). Отложено.
- **event-агенты** - у них нет живой сессии; фичи неприменимы. Кнопка "Сводка" для event-агента показывает только механический статус, кнопки reply-вброса нет.

## Риски и открытые вопросы

- **Очередь при вечно занятом агенте:** если pane никогда не idle, комментарии копятся. Митигация: TTL/кап очереди + пометка в сводке "N недоставленных". Обсудить кап.
- **Гонка дренажа и старт-кика:** и то и то шлёт send-keys на idle. Дренаж должен идти ПОСЛЕ старт-кика в одном проходе reconciler'а, чтобы не перебить kick. Сериализовать в одной секции прохода.
- **Множественные сообщения:** по одному за проход (интервал прохода reconciler'а - 60 с) - при пачке комментариев доставка растянется на минуты. Приемлемо для наставлений.
- **fingerprint-гейт хрупок:** зависит от вида prompt claude (`/rc active|❯`). Если UI claude сменится - гейт молчит, доставки нет. Наследуем существующий риск старт-кика.

## Дополнение по итогам second-opinion (codex, 2026-07-19)

Источник: `docs/dev/consult-report-hermes-borrow.md` (сверка подходов с Hermes Agent). Три уточнения к спеке, входят в объем этапа 1:

**1. Семантика доставки - явно at-least-once.** Между `send-keys` и durable-пометкой "доставлено" exactly-once недостижим: пометка ПОСЛЕ send-keys дает дубль при падении reconciler'а между ними, пометка ДО - потерю. Принимаем at-least-once: пометка после send-keys, а в вбрасываемый маркер включается id сообщения (`[оператор #<id>]: ...`); AGENT.md дополнить строкой "повтор наставления с тем же id - игнорируй". Окно дубля - только crash между send и mark, цена дубля - повторное наставление; приемлемо.

**2. Усиление map (вариант A).**

- ключ - пара `(chat_id, message_id)`, не голый `message_id`;
- TTL по времени (напр. 14 дней) вместо кольца на 200 записей; запись atomic (tmp+rename, как реестр);
- map-запись писать для КАЖДОГО отправленного чанка (длинная сводка бьется на несколько sendMessage - reply возможен на любой);
- reply-якорь - только неизменяемые сообщения (статус/сводка). Редактируемое inline-меню якорем не является: бот редактирует одно и то же menu-сообщение при переходах root -> агент A -> агент B, reply на него даст stale-роутинг. Menu-сообщение либо не регистрировать в map, либо обновлять запись при каждом edit.

**3. Наблюдаемость очереди.** В механическую сводку (фича 1) добавить: глубина `mission-inbox/`, возраст старейшего недоставленного, время последней попытки дренажа; флаг `delivery_stalled`. По капу решение пересмотрено adversarial-гейтом (см. ниже): кап с backpressure на put; TTL-выбрасывания нет - старые наставления не теряем молча, показываем возраст.

**Заметка на следующий этап (outbox):** формулировка "notify не проложен" в разделе "Вне объема" неточна - generic `claude-agent-tgbot notify` уже существует и используется дайджестом лимитов. Строить нужно не второй транспорт, а agent-scoped слой над существующим (`agent-outbox put <agent>`: атрибуция, durable-очередь, доставка доверенным процессом - миссия с Bash не должна уметь выдавать себя за другого агента). Детали - `docs/plan-2026-07-19-hermes-borrow.md`.

## Правки по adversarial-гейту (codex, 2026-07-19)

Прогон по постановке выполнен: 22 атаки (2 critical, 15 major, 5 minor), отчет - `docs/dev/adversarial-report-stage9.md` (локально). Опорные привязки верифицированы по коду. Правки ниже - нормативные, при противоречии перекрывают текст выше.

### Критические

1. **Явная адресация pane (`-t`).** Все tmux-вызовы дренажа и сводки - строго с `-t` на pane, зафиксированный при создании сессии (pane-id хранить в state). Сокет `-L agent-<name>.g<gen>` изолирует агентов друг от друга, но внутри сервера attach оператора со split'ом делает "current pane" непредсказуемым: без `-t` текст с Enter может уйти в shell-pane и исполниться как команды. Тот же дефект у существующего старт-кика (`claude-agent-reconciler:1056-1062`) - фиксить в рамках текущей перестройки reconciler, отметить в ее бэклоге.
2. **Подтверждение доставки по SM §13.1, а не "после send-keys".** send-keys - UI-RPC без ack (`design-2026-07-11-agent-state-machine.md:414`). Протокол дренажа: (а) capture-pane -t: prompt idle И input-строка пуста; (б) `send-keys -l` текст с маркером; (в) capture-pane: маркер виден в input-строке, иначе Enter НЕ слать (2 неудачи -> attention, fail-closed); (г) Enter; (д) durable-пометка delivered. Остаточное окно дубля - crash между (г) и (д) - принятый at-least-once, гасится дедуп-id. Recovery черновика: input-строка непуста и содержит наш маркер -> дослать Enter (crash между (б) и (г)); непуста и НЕ маркер -> не дренировать (оператор печатает по attach).

### Major

3. **Fingerprint якоренный:** пустая input-строка + prompt-паттерн в последней строке; не unanchored `grep '/rc active|❯'` по `tail -6` (ловит ❯ в выводе и частично набранный текст).
4. **Kick и drain взаимоисключающи** для агента в одном проходе: после kick дренаж только со следующего прохода (UI уходит в busy асинхронно, немедленный capture может еще видеть idle).
5. **Framing вброса:** маркер-префикс `[оператор #<id>]: ` гасит ведущие `/` `!` `#`; `\n` нормализуется в литерал `\n`, C0-символы выпиливаются (иначе send-keys отправит фрагменты промежуточными Enter); входной лимит длины на put.
6. **Протокол очереди - как spool (stage4):** атомарный seq-резерв, `msg-%06d.json` (zero-padded, FIFO по numeric sort), tmp -> fsync -> rename -> fsync(dir). Кап N=50: put сверх капа отвергается, бот отвечает оператору отказом (backpressure вместо тихого роста до ENOSPC на одной FS с control-plane).
7. **Дедуп доставки - durable ledger** доставленных id рядом с очередью; проверка перед send. Инструкция дедупа в AGENT.md - вторая линия, не механизм (после compaction агент id не помнит).
8. **Map-запись:** имя + generation агента; при доставке сверять живую инкарнацию (реюз имени в TTL-окне не должен отдать старый reply новой миссии). Запись map - сразу после sendMessage, до продвижения offset; `send_message` должен возвращать message_id всех чанков (сейчас отбрасывает, `claude-agent-tgbot:76-83`).
9. **Reply-роутинг до командного парсинга:** reply с текстом, похожим на команду, - комментарий, не команда.
10. **Отказ mission-put - транзиентный класс** (как `TransientSpoolError`): offset НЕ продвигать; сейчас generic Exception в цикле бота продвигает offset и теряет update (`claude-agent-tgbot:429-431`).
11. **Поля сводки:** `phase`/`claim`/`iterations` живут в `state.<gen>.json`, не в `control.json` (исходный список выше - поправить при реализации). Cross-file снапшот: поколение берется ОДНИМ чтением control, state читается строго этого поколения, без перечитываний.
12. **События в TG - только через redaction на экспорте** (маскирование секрет-паттернов; `revise --note` хранится сырым by design) + чтение хвоста файла ограниченно, не `readlines()` целиком; chunk-split HTML - по границе escape-entity (наивный `body[i:i+3800]` рвет `&amp;` посередине).
13. **delivery_stalled:** очередь непуста И возраст старейшего > 10 мин И последняя попытка неуспешна; сброс при успешной доставке.

### Minor (решения зафиксированы)

- `edited_message` игнорируется осознанно: правка комментария не доезжает и не должна (обработка edited = новый update_id = дубль).
- Кнопка "Сводка" шлет НОВОЕ сообщение (sendMessage), не editMessageText меню - это же дает неизменяемый reply-якорь.
- Reply на сообщение, отправленное до введения map, - вежливый отказ ("сопоставить не могу, ответьте на свежую сводку").
