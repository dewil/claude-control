# LIM - дайджест лимитов LLM

Домен покрывает снятие остатка подписочных лимитов Claude Code и Codex,
сглаживание шумных провайдерских данных, панель в Telegram и внесхемное
чтение того же кэша командой `/limits`.

## Границы

**Входит:** периодический пробник остатка лимитов (`bin/claude-agent-limits-digest`),
монотонный клэмп на занижения реплик провайдера, кэш последнего снимка,
рендер панели (проценты, градусник, память хоста), дедуп отправки по
сигнатуре, автовосстановление протухшего Claude-токена дешевым прогоном.

**Не входит:**

- сама отправка сообщения в Telegram (транспорт, whitelist, форматирование
  карточек бота) - `BOT/tgbot.md`, здесь только факт вызова
  `claude-agent-tgbot notify --pre`;
- живучесть таймера как systemd-юнита, сторожа, жнец зомби - `RECON/reconciler.md`;
- дайджест канона (`~/.claude-control/canon/digest/`) - тот же термин
  "дайджест", другой домен (`CANON`), общего кода нет.

## Инварианты

- **INV-LIM-01.** Пробник снимает остаток раз в 15 минут
  (`claude-agent-limits-digest.timer`, `OnCalendar=*:0/15`), а не чаще.
  Довод: Claude usage-эндпоинт держит rate-limit порядка 1 запроса/180с;
  15 минут дают запас без риска забанить собственный опрос.
- **INV-LIM-02.** Панель уходит в Telegram только при изменении сигнатуры
  (проценты/статусы), а не на каждый тик таймера; сброс окна (reset) сам по
  себе изменением не считается. Довод: безусловная отправка раз в 15 минут
  превращает канал в шум и глушит внимание к реальным изменениям.
- **INV-LIM-03.** Внутри одного окна остатка процент расхода только растет:
  клэмп держит бегущий минимум `remaining` с последнего `resets_at` и не
  дает занижению реплики провайдера снизить показанный расход. Довод:
  зафиксированный на практике рассинхрон бэкенд-реплик OpenAI переключает
  видимое значение на часовом масштабе в обе стороны без смены окна;
  без клэмпа панель показывает то падение, то рост расхода в одном и том
  же окне, что физически невозможно.
- **INV-LIM-04.** Смена окна распознается по близости `resets_at` с
  допуском `WINDOW_MATCH_S` (300 секунд), а не по строковому равенству.
  Довод: момент "сейчас + остаток", которым провайдер считает конец окна,
  дрейфует на секунды между опросами; сравнение строк никогда не совпадало
  бы и клэмп молча не работал бы вовсе (найдено 2026-08-02).
- **INV-LIM-05.** Клэмп сбрасывается только при смене `resets_at` за
  пределами допуска (новое окно), никогда - по одному лишь падению
  `used` без смены окна. Довод: заниженная реплика способна отдать
  реальное прошлое значение того же окна (например, близкое к нулю в
  начале недели), и авто-сброс по такому сигналу неотличим от настоящего
  сброса окна - вернул бы те самые качели, которые клэмп призван погасить.
- **INV-LIM-06.** Длина окна известна константами кода
  (`WINDOW_SECONDS = {"time": 5ч, "week": 7д}`), а не приходит от
  провайдера. Довод: провайдер отдает только момент сброса, не длину окна;
  величина градусника ("докуда дотикали часы") без явной длины окна
  вычислена быть не может.
- **INV-LIM-07.** Токены провайдеров (Claude OAuth, Codex auth) никогда не
  попадают в снапшот, кэш или панель - только проценты остатка и время
  сброса. Довод: кэш и панель могут утечь в чат/лог/скриншот; токен в них -
  прямой секрет по `secrets-handling.md`.
- **INV-LIM-08.** На получении 401 от Claude-эндпоинта пробник один раз
  дергает дешевый прогон `claude -p` (штатный CLI-рефреш
  `~/.claude/.credentials.json`) и повторяет запрос, прежде чем считать
  токен протухшим. Статус `stale` означает именно "рефреш не помог", а не
  первую же 401. Довод: без само-рефреша токен протухал бы при простое
  VM и требовал ручного вмешательства на каждый обычный простой ночью.
- **INV-LIM-09.** Codex-токен живет на LUKS-томе (`/data/.codex/auth.json`)
  и при запертом томе секция Codex показывает явный статус "том заперт",
  но остальной дайджест (Claude-секция, память хоста) продолжает приходить.
  Таймер не зависит от смонтированности `/data`. Довод: асимметрия
  хранения токенов (Claude на корне, Codex на шифрованном томе) не должна
  останавливать весь дайджест из-за одного запертого раздела.
- **INV-LIM-10.** Рендер панели умеет два независимых режима: `once`
  (снять+сравнить+возможно отправить, с рубильником
  `CLAUDE_AGENT_LIMITS_ENABLED`) и `render` (собрать панель из уже
  сохраненного кэша без сетевого похода к провайдерам). `/limits` бота
  использует только второй режим. Довод: команда пользователя из чата не
  должна тратить rate-limit провайдера и не должна зависеть от сетевой
  доступности в момент запроса.
- **INV-LIM-11.** Данные считаются устаревшими (`stale`, порог
  `CLAUDE_AGENT_LIMITS_STALE_MIN`, дефолт 45 минут) в `render`, если кэш не
  обновлялся дольше порога. Довод: без явного порога "устарело" молчаливый
  таймер, переставший тикать (упавший systemd-юнит), выглядел бы для
  пользователя как последнее известное состояние, а не как отказ.
- **INV-LIM-12.** Округление чисел панели идет по правилу
  `php_round` (half-away-from-zero), не по питоньему `round`
  (half-to-even). Довод: порт форматтера с PHP на Python 1:1 - иное
  округление сдвигает бар градусника на пограничных процентах (например,
  на 45%) без изменения входных данных, то есть портит визуальную
  сверку "то же число - тот же бар".
- **INV-LIM-13.** Отправка каждой панели логирует причину строкой вида
  `шлем: claude.five_hour 3->5`, а не просто факт отправки. Довод: без
  причины в логе невозможно отличить дедуп-логику, которая молчит
  правильно, от дедуп-логики, которая молчит из-за сломанного сравнения
  сигнатур - тот самый класс тихого отказа, что уже случался с
  `resets_at`-строками.

## Внешние контракты

- **Читает:** Claude OAuth/usage-эндпоинт, Codex `wham/usage`-эндпоинт
  (оба - через mihomo, `LIMITS_PROBE_PROXY`, дефолт `http://127.0.0.1:7890`);
  `~/.claude/.credentials.json` (Claude-токен); `/data/.codex/auth.json`
  (Codex-токен, требует смонтированного `/data`); env-переменные
  `CLAUDE_AGENT_LIMITS_TZ`, `CLAUDE_AGENT_LIMITS_ENABLED`,
  `CLAUDE_AGENT_LIMITS_STALE_MIN`, `LIMITS_PROBE_PROXY`,
  `LIMITS_PROBE_CLAUDE_CREDS`, `LIMITS_PROBE_CODEX_AUTH`,
  `LIMITS_PROBE_DATA_MOUNT`, `LIMITS_PROBE_CLAUDE_UA`;
  учетные данные бота `CLAUDE_AGENT_TG_TOKEN`/`_WHITELIST`/`_PROXY`.
- **Пишет:** кэш снимка `~/.claude-control/limits/last.json`; стейт клэмпа
  `~/.claude-control/limits/clamp.json` (ключ вида
  `claude:seven_day`/`codex:scoped:fable`); панель в личку оператора через
  `claude-agent-tgbot notify --pre`; лог решения об отправке в journalctl.
- **systemd:** `claude-agent-limits-digest.timer` (`OnCalendar=*:0/15`,
  `Persistent=true` - наверстывает пропуск после простоя хоста).
- **CLI:** `claude-agent-limits-digest {once [--dry-run], render}`; `/limits`
  в `claude-agent-tgbot` вызывает `render` из кэша, сети не трогает.

## Решения

- **2026-07-17.** Дайджест лимитов переехал целиком в claude-control
  (`bin/claude-agent-limits-digest`) с прежней цепочки
  llm-probe -> POST adm -> cactus-digest; старые юниты и файлы на VM
  удалены, в cactus-adm выставлен `MONITORING_LIMITS_DIGEST_ENABLED=false`.
  Демонтаж кода в cactus-adm - по отдельному handoff, только по явному
  запросу пользователя.
- **2026-07-18 (commit be4f068).** Протухший Claude-токен чинится
  само-рефрешем перед тем, как объявляться `stale` (INV-LIM-08).
- **2026-07-23 (commit e382113).** Монотонный клэмп на занижения реплик
  Codex (INV-LIM-03..05) - реализован и задеплоен после наблюдения
  качелей 16%->6%->16% в течение одной ночи без смены окна.
- **2026-07-30 (commit ccb8b8d).** Вторая величина градусника - пройденное
  время окна (`┃`/`█`/маркер разрыва от 20пп) вместо одного только
  остатка; заливка "занятое" вместо "свободное" для памяти хоста, тем же
  визуальным языком.

## Известные дыры

- Память проекта (`project_llm_limits_dashboard`, обновлена 2026-07-30)
  все еще называет частоту "каждые 30 мин" в описании записи, тогда как
  runbook и код (`.timer.tmpl`) однозначно говорят про `*/15`. Это
  расхождение внутри источников замысла, не между замыслом и кодом:
  вероятно, память не обновлена после смены частоты. Спека берет более
  свежий и более авторитетный источник (runbook + код); саму запись
  памяти никто не правил в рамках этой задачи.
- Единственная теоретическая дыра клэмпа, названная в памяти проекта:
  `used` падает почти до нуля БЕЗ смены `resets_at` - внутренне
  противоречиво для реального провайдера и оставлено без защиты
  намеренно (см. INV-LIM-05, довод там же).
- Ручной фолбэк на порчу клэмпа - удаление `clamp.json` (пересевается с
  нуля, теряя накопленный минимум) - не автоматизирован и не имеет
  собственной диагностики "клэмп выглядит подозрительно, возможно стоит
  сброса"; решение всегда принимает человек по наблюдаемым качелям.

## Трассируемость

`tests/test-agent-limits-digest.sh` существует и содержит golden-panel
тесты форматтера и отдельный блок тестов клэмпа (`clamp first passthrough`,
`clamp holds min on spurious rise`, `clamp resets on new window`,
`clamp survives resets_at jitter`, `clamp tolerates minutes of drift`,
`clamp survives unparsable reset`, `clamp skips window without reset`,
`clamp ignores error section`, `clamp scoped by label` и симметричные для
`_elapsed_percent`/`_fmt_countdown`), но ни один тест не несет тег
`INV-LIM-NN` по схеме `requirements-traceability.md`.

| Инвариант | Покрытие |
|---|---|
| INV-LIM-01 частота 15 мин | нет теста (частота задана таймером, не проверяется юнит-тестом) |
| INV-LIM-02 дедуп по сигнатуре | нет тега; логика дедупа в коде, отдельного теста не найдено при точечном поиске |
| INV-LIM-03 клэмп держит минимум | нет тега; тесты "clamp holds min on spurious rise", "clamp tracks real usage" |
| INV-LIM-04 допуск WINDOW_MATCH_S | нет тега; тесты "clamp survives resets_at jitter", "clamp tolerates minutes of drift" |
| INV-LIM-05 сброс только по смене resets_at | нет тега; тест "clamp resets on new window" |
| INV-LIM-06 длина окна константами | нет тега; `WINDOW_SECONDS` используется в `_elapsed_percent`-тестах |
| INV-LIM-07 токены не попадают в кэш/панель | нет тега; нет отдельного теста, проверялось бы построчным осмотром вывода |
| INV-LIM-08 само-рефреш на 401 | нет тега; нет юнит-теста (требует сетевого мока 401, не найден) |
| INV-LIM-09 asimметрия хранения токенов, Codex не блокирует Claude | нет тега; нет теста в этом наборе |
| INV-LIM-10 once vs render | нет тега; нет прямого теста разделения режимов |
| INV-LIM-11 stale-порог | нет тега; нет теста |
| INV-LIM-12 php_round | нет тега; golden-panel тесты неявно проверяют бар на конкретных процентах |
| INV-LIM-13 лог причины отправки | нет тега; нет теста на формат строки лога |

## Вопросы к пользователю

1. Память проекта называет частоту "каждые 30 мин" против фактических 15 -
   поправить запись памяти сейчас (за рамками этой задачи со спеками) или
   оставить как есть до отдельного прохода по памяти?
2. INV-LIM-07 (токены не попадают в кэш/панель) сформулирован от замысла,
   но не был сверен построчным чтением кода экспорта - нужен ли отдельный
   аудит домена (`codex-audit`) именно на этот инвариант до следующего
   релиза, учитывая что нарушение - прямая утечка секрета?
3. Разметка тестов тегами `INV-LIM-NN` - делать отдельной задачей сейчас
   или откладывать до аудита домена?
4. `WINDOW_MATCH_S=300` и `CLAUDE_AGENT_LIMITS_STALE_MIN=45` (дефолт) -
   фиксировать эти числа как часть инварианта (что и сделано выше) или
   держать как параметр эксплуатации без гарантии в спеке?
5. INV-LIM-05 (нет авто-сброса при падении used без смены окна) назван
   инвариантом с полным доводом из памяти проекта - подтвердить, что это
   именно принятое решение "не чинить" (по формулировке sdd-pipeline.md,
   решение "не чинить" тоже убирает дыру), а не отложенная работа с
   открытым TODO?
6. Нужен ли инвариант на поведение при полностью недоступном провайдере
   (`error`-секция) - сейчас код "не трогает стейт клэмпа", но явного
   пользовательского контракта "что видит оператор в панели при обеих
   секциях в error" в источниках не нашлось - актуален ли отдельный
   инвариант или текущее поведение и так очевидно из формата панели?
