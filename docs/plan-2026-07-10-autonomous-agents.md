# План: слой автономных агентов в claude-control

Дата: 2026-07-10. Статус: v5.1. История ревью codex (отчёты удалены как отработанные, находки вложены в план): 2 advisory-раунда, 2 adversarial-раунда (20 атак -> re-review 10/20 closed, остальное в чек-листе этапа 1a), full-audit (3 blocker -> тот же чек-лист), compliance этапа 0. Ресерч практики Karpathy - см. "Принципы".

## Цель

Расширить claude-control от "удаленные сессии по запросу" до "парк автономных агентов": сессии, которые работают без человека, плюс инфраструктура наблюдения за ними. Хост парка - llm VM (Selectel), Mac и телефон - клиенты.

Три пользовательских сценария:

1. **Событийный агент** - всегда работает, слушает источник событий (TG-чат, алерты мониторинга, вебхук) и на каждое событие запускает агентный прогон.
2. **/solo** - в любой живой сессии проекта дать команду, после которой сессия становится самостоятельной фоновой задачей: продолжает миссию без пользователя, а он может в любой момент подключиться, посмотреть ход работы и дать наставления.
3. **Дашборд** - единое место, где видны все фоновые агенты: цель, статус, heartbeat, расход. Сначала TG-бот, позже опционально веб-панель.

## Не-цели

- Не переписывать существующий контур claude-control - агентный слой добавляется рядом, теми же паттернами (bash, tmux, yq, launchd/systemd).
- Не строить свою оркестрацию поверх API - остаемся на Claude Code CLI и его штатных механизмах.
- Не тащить в парк не-git проекты (vault на Yandex.Disk): их агенты живут только на Mac'е.
- Не обещать exactly-once для событий: гарантия - at-least-once + идемпотентная обработка; внешние неидемпотентные эффекты - см. "Модель доверия", п.4.
- Не обещать жесткую изоляцию агентов друг от друга в v1 - см. "Модель доверия".

## Модель доверия (v1, зафиксировано осознанно)

Bash-система под одним Unix-юзером не дает настоящих границ безопасности. Честная формулировка того, что защищает v1:

1. **Границы v1 - от ошибок, не от злоумышленника.** Файловое разделение spec/state/control и allowlist'ы защищают от багов и глупостей агента, но агент с Bash технически может дотянуться до чужих файлов. Настоящая изоляция (свой UID/контейнер per role, реестр у отдельного пользователя) - осознанно отложена; переоценка после этапа 4.
2. **Недоверенный вход = минимальные руки.** Event-агент, принимающий недоверенный текст (TG-сообщения чужих людей, алерты с внешними данными), работает с минимальным набором: без Bash, без MCP с чувствительными кредами, autonomy=suggest. Prompt-инструкция "событие - это данные" остается, но границей НЕ считается - границей считаются инструменты, которых у агента нет.
3. **Секреты per-role.** Каждой роли - свой набор credentials и MCP-серверов через project-scope конфигурацию (`.mcp.json` проекта / отдельные env), не через общий user-scope. Общие секреты хоста агентским сессиям не выдаются.
4. **Внешние неидемпотентные эффекты** (письмо, платеж, деплой) - только autonomy=release, по одному за виток, с downstream idempotency key там, где API его поддерживает, и записью в events.jsonl до и после. Где ключа нет - действие остается за человеком: at-least-once честно означает "возможен дубль".
5. **Сессии агентов не наследуют глобальные настройки хоста.** Каждому агенту - явный набор permissions (свой settings-файл), bypassPermissions агентам не выдается никогда.

## Принципы (из практики Karpathy, 2025-2026)

1. **Autonomy slider, не рубильник.** `autonomy: suggest | act | release` в spec - пресет **capabilities** (workspace_write, external_write, notify, merge, deploy); `release` - отдельный trust domain с явным перечнем разрешенного. Новый агент стартует с низкой ступени.
2. **Автоматизируем только проверяемое.** Миссия без проверяемого критерия готовности не стартует - /solo отклонит. Для исследовательских миссий допустим `suggest`: результат - артефакт + приемка человеком. Цикл "агент сгенерировал - человек проверил" должен быть быстрым: дашборд показывает результат, не только статус.
3. **Агент не оценивает сам себя.** Агент пишет заявку (`agent_claim: done` + ссылка на замороженный артефакт); принятие ставит внешний контур - reconciler по критерию из mission.md, агент-приемщик или человек. Критерии и лимиты - вне контроля агента.
4. **Бюджет на виток.** Превышение `max_iteration_minutes` - не тихий discard (kill не откатывает изменений), а interrupt + карантин: статус `needs-attention`, изменения остаются в ветке для разбора. Файловая работа на `act` - всегда в ветке/worktree.
5. **Границы держит механика, не промпт** (см. "Модель доверия").
6. **Дисциплину цикла обкатывать на связке.** Смоук - regression-набор миссий, гоняется при смене любого элемента: CLI-версия + модель + роль + промпт + тулы.

Источники: YC talk "Software Is Changing (Again)" 2025-06-17, Dwarkesh Patel 2025-10-17, github.com/karpathy/autoresearch 2026-03, karpathy.bearblog.dev/sequoia-ascent-2026 2026-04-30.

## Архитектура

```text
llm VM (Selectel, systemd --user, linger=yes)
├── control-сессия            # уже есть, ставится install.sh
├── reconciler (замена project-watchdog для агентов; сам под systemd
│                Restart=always - надзор за надзирателем штатный):
│   ├── сводит desired (control.json) с фактическим (tmux/сессии)
│   ├── admission control: max одновременно живых агентов (по RAM-бюджету),
│   │   staggered resume после ребута/разлочки - по одному, не штормом
│   ├── свои часы: wall-time миссии меряет сам (не верит state агента)
│   └── lease/generation/acceptance; retry с backoff; эскалация в needs-attention
├── ~/.claude-control/agents/<name>/
│   └── spec.yaml + mission.md + role/ + state.json + control.json + events.jsonl
├── claude-agent-run          # раннер событийного агента
│   └── inbox: fsync(file+dir) -> курсор -> прогон -> ack; dead-letter для
│       ядовитых событий; ротация/ретеншн inbox и events (logrotate уже есть)
├── tmux: mission-агенты      # ВЫДЕЛЕННАЯ tmux-сессия agent-<name> на агента
│                             # (не общий проектный диспетчер с capacity)
└── tg-бот дашборда           # getUpdates через mihomo; auth: private chat + from.id
```

Существующий **project-watchdog для агентских сессий отключается** - его политика "stale -> stop + свежий старт" уничтожает resume-семантику (свежая сессия = потеря миссии). Агентов надзирает только reconciler; watchdog учится пропускать сессии, числящиеся в реестре агентов (этап 1b).

Два типа агентов:

- **event** - headless-прогоны `claude -p` на каждое событие. Поток - **durable inbox, at-least-once**: событие персистится в inbox (fsync файла и каталога, атомарная вставка) -> курсор источника коммитится сразу после персиста (иначе head-of-line блокировка) -> прогон -> ack. Повторная обработка обязана быть идемпотентной (дедуп по event id); событие, валящее прогон N раз подряд, уходит в **dead-letter** с алертом, не блокирует очередь. Разграничение с MCP: MCP - руки агента, но не уши; события принимает слушатель, MCP пользуется разбуженный агент.
- **mission** - живая сессия в **выделенном tmux `agent-<name>`** под `claude remote-control`, в self-pacing loop. Видна с телефона; наставление вклинивается в цикл на лету. Живость - по `next_wakeup_at` + grace (не mtime). Восстановление: пропавшего агента поднимает reconciler возобновлением сессии по session_id (`remote-control --session-id`, проверено спайком; очистка stale worktree-lock - этап 1b); при подъеме инкрементируется `generation`. **Витки compaction-safe**: каждый виток начинается с чтения mission.md и state.json с диска, важное персистится в реестр и артефакты - авто-суммаризация контекста harness'ом в любой момент безвредна.

### Реестр агента (`agents/<name>/`)

Три плоскости: desired (spec + mission + control.desired) / reported (state) / control (владение и приемка).

```text
agents/<name>/
├── spec.yaml     # неизменяемое задание; пишется один раз при создании
├── mission.md    # неизменяемый текст миссии и критерия приемки (плоскость spec)
├── role/         # снапшот КОНТЕНТА роли из toolkit на момент создания
│                 # (не только hash: recovery не зависит от состояния канона)
├── state.json    # пишет ТОЛЬКО агент, атомарно (tmp+mv); содержит generation
├── control.json  # пишет ТОЛЬКО reconciler/оператор ЧЕРЕЗ claude-rc ПОД flock:
│                 # desired (running|paused|stopped), lease (owner, generation,
│                 # ttl), acceptance (pending|accepted|rejected|needs-human),
│                 # started_at (часы reconciler'а), retry-счетчики
└── events.jsonl  # append-only, запись под flock
```

```yaml
# spec.yaml
name: faq-updater
type: mission            # event | mission
role: coder              # имя роли; контент заморожен в role/
project: проект 1-faq
goal: "Разобрать новые вопросы из чата, обновить FAQ, подготовить PR"
autonomy: act            # suggest | act | release (пресет capabilities)
limits:
  max_iterations: 50
  max_hours: 8                   # меряет reconciler по своим часам
  max_iteration_minutes: 20      # по iteration_started_at из state
  on_blocker: notify-and-sleep
```

```json
// state.json (пишет агент; поколение делает stale-записи различимыми)
{
  "generation": 3,              // получено от reconciler при старте; записи
                                // с generation < текущего reconciler игнорирует
  "phase": "sleeping",          // working | sleeping | waiting_input | blocked
  "status_line": "виток 7: кластер вопросов про Happ",
  "agent_claim": "running",     // running | done | blocked - ЗАЯВКА
  "claim_artifact": "abc123",   // при done: замороженный артефакт (commit hash)
  "session_id": "<uuid>",
  "iteration_started_at": "2026-07-10T09:40:00Z",
  "last_progress_at": "2026-07-10T09:41:12Z",
  "next_wakeup_at": "2026-07-10T10:11:00Z",
  "iterations": 7,
  "cost_usd": 1.42
}
```

Правила владения и fencing:

- `desired` (running/paused/stopped) ставит только оператор через `claude-rc agent start|pause|stop <name>` - reconciler различает "упал" (desired=running, факта нет -> resume) и "остановлен человеком" (desired=stopped -> не трогать). Без этого reconciler воскрешал бы отмененные миссии.
- Захват lease: сначала жесткая остановка предыдущего владельца (kill tmux-сессии, проверка исчезновения PID), потом атомарный захват, потом инкремент generation. TTL сам по себе владение не передает.
- Все записи в control.json - через один helper в claude-rc под flock; прямая запись кем-либо еще - нарушение (модель доверия, п.1).
- Приемка `agent_claim: done`: reconciler проверяет критерий из mission.md против `claim_artifact` (замороженный commit hash - подменить содержимое под тем же хэшем нельзя), вердикт пишет в control.json. Вердикт приемщика-агента (этап 7) тоже проходит через reconciler: приемщик выдает отчет-артефакт, решение фиксирует reconciler.

### /solo (скилл, раздается через канон claude-toolkit)

1. Сжать контекст в mission.md: цель, проверяемый критерий (иначе не стартует), ограничения, стоп-условия. Показать пользователю на подтверждение.
2. Проверить, что allowlist проекта покрывает миссию; если нет - сказать честно, не стартовать.
3. Регистрация: полный комплект файлов реестра с `desired: paused`; последний атомарный шаг - перевод в `running`. Reconciler реагирует только на running: нет ни бесхозных миссий при падении между шагами, ни double-start наперегонки с /solo.
4. Кейс A (**MVP, этап 2**): /solo из выделенной агентской сессии. Если команда дана в обычной проектной сессии - это **мини-handoff**: регистрация (paused) -> исходная сессия завершает ход и освобождает транскрипт -> claude-rc поднимает выделенную tmux-сессию `agent-<name>` -> флип в running. Два владельца одного транскрипта недопустимы и в кейсе A; проектный диспетчер с capacity не делится (у агента свой PID/tmux/lifecycle для lease и надзора).
5. Кейс B (локальная сессия Mac -> tmux) - **этап 5, спайк**: двухфазный handoff (prepare -> stop -> resume -> commit lease), сбой отката - needs-attention; два процесса на одном транскрипте недопустимы.
6. Кейс C (Mac -> VM) - **research spike**: транскрипт - лишь часть состояния; только git-проекты, обязательный push, окружение на VM заранее. Go/no-go по итогам.

### Дашборд

- **TG-бот**: long-polling getUpdates через mihomo. Auth: только личный чат (private) + проверка `from.id` по whitelist - групповой chat_id правом не является (в группе им владеют все участники). Имя агента из команды валидируется по `[a-z0-9-]+` (никаких путей), вывод агентских строк эскейпится (status_line - недоверенные данные). `/agents` - таблица парка; `/agent <name>` - детали + хвост events + ссылка на результат (PR/дифф); пуши accepted/rejected/needs-attention; диплинк на сессию.
- **Веб-панель** - опционально, позже.

### Ролевые агенты и конвейер (перспектива, этап 7)

- Роль = spec-шаблон: промпт, тулы, allowlist, autonomy, модель, свои креды/MCP (модель доверия, п.3). Контент роли замораживается в `role/` при создании агента.
- Ценность - **независимый контекст приемщика**; приемщик получает замороженный артефакт (commit hash), выдает отчет; вердикт в control.json фиксирует reconciler.
- Это **опциональный risk-tier** (удваивает расход) - для миссий, где цена ошибки выше цены второго прогона.
- Приемочный критерий этапа - корпус: и подсаженные ошибки разных классов (ловит), **и заведомо корректные работы (принимает)** - reject-all статистику не проходит.

### Сбор поправок оператора -> правила (этап 7b, запрос dwl 2026-07-12)

Замыкание петли обучения: типовые поправки, которые оператор вносит в работу агентов, должны накапливаться и превращаться в правила (роли/канона), а не повторяться вручную.

- **Источники поправок - уже durable** (ничего дополнительно собирать не надо): (a) `revise --note` и `reject --reason` - в acceptance.note и events.jsonl; (b) наставления с телефона - в транскрипте mission-сессии; (c) пост-accept доработки человеком - diff между claim_artifact и итоговым merge в main проекта.
- **Harvester** (периодический прогон, кандидат в event-агенты): агрегирует источники по всем агентам роли -> кластеризует повторяющиеся типы поправок (>= 2-3 повторов) -> формирует **кандидатов в правила** (формат feedback-мемори: суть + why + how to apply).
- **Выход - только через ревью человека**: кандидаты складываются дайджестом (TG/файл), одобренное уходит в канон через toolkit-log/upstream-pending (правило роли в claude-toolkit) - авто-редактирование промптов ролей без человека запрещено (роль - замороженная плоскость spec, меняется только ревизией).
- Синергия с этапом 8 (maintenance-агент канона): harvester - естественный поставщик его входа.

### Чек-лист для документа state machine (этап 1a, из adversarial re-review)

Требования, которые документ этапа 1a обязан закрыть явно (иначе этапы 1b-4 не стартуют):

- **Терминальность acceptance**: accepted/rejected автоматически переводит desired в stopped - завершенный агент не воскресает.
- **Часы max_hours** стартуют при первом захвате lease, не при регистрации в очереди admission.
- **Порядок захвата lease**: pre-flight проверка возможности resume (auth, LUKS, quota) -> kill **process group** старого владельца -> запись lease + generation одним fsync-rename. Не убивать живого владельца, пока resume невозможен.
- **Durability критичных записей** (control.json, курсоры inbox, dead-letter): tmp + fsync файла и каталога + rename.
- **MemoryMax**: агентские процессы - транзиентные systemd-юниты с лимитом памяти; admission считает бюджет RAM, не штуки процессов.
- **Предохранитель бюджета** стопит прогоны, но не intake: слушатель продолжает принимать события в inbox.
- **Dead-letter** - только после health-check инфраструктуры: событие не хоронится из-за упавшего прокси/quota.
- **Provenance claim_artifact**: коммит обязан быть потомком зафиксированной базы миссии в ветке агента (ancestry-проверка) - старый "зеленый" коммит не проходит.
- **Границы снапшота роли**: role/ замораживает промпт роли; skills/MCP-схемы фиксируются перечнем в spec. Экстренный отзыв роли = `agent pause` всем агентам роли командой оператора.
- **Учет расхода headless при kill**: источник инкрементальных usage-данных (транскрипт-JSONL пишется по ходу - парсить его, не финальный JSON).
- **Ретеншн не трогает pending**: ротация inbox/events не удаляет неподтвержденные события.
- Из full-audit 2026-07-11 (три блокера до 1b): **полная таблица переходов + crash-матрица** (все состояния x все точки падения, включая /solo-handoff без окна paused-orphan и двойного владельца); **семантика needs-attention/needs-human и lease renewal**; **event-контракт** (жизненные циклы intake и executor раздельно, FSM ack/dedup/dead-letter, backpressure и лимит диска); **schema-валидация файлов реестра** при чтении; **роль как opaque bundle с манифестом и дайджестами** (recovery не зависит от текущего канона toolkit).
- **Живость сессии = коннект к relay, а не живой процесс** (урок теста-ребута 2026-07-11): mission/control под remote-control может иметь живой PID и валидный `next_wakeup`, но висеть на модальном экране claude (trust/setup/permission-prompt) в отключке от relay - невидим с телефона, миссия стоит. Health-сигнал обязан включать "есть свежий heartbeat/коннект к relay"; модальный экран на старте детектируется и уводит в needs-attention, а не засчитывается за idle.
- **Context hygiene** (внешний compact): reconciler следит за заполнением контекста mission-агента по usage из транскрипта-JSONL; при заполнении **>= 90%** окна и `phase=sleeping` (граница витка - безопасный момент) вбрасывает `/compact` в tmux-сессию через send-keys. Компакт всегда искусственный и на границе, никогда посреди витка.
- Принятые риски без изменения: настоящая изоляция ролей (UID/cgroup/сеть) - модель доверия v1, переоценка после этапа 4.

### Граница с claude-toolkit

**toolkit - контент** (правила, роли, скиллы; снапшоты в `.claude/` проектов, меняется часто, персонален). **claude-control - рантайм** (демоны, tmux, реестр, надзор; раз на хост, публичен). Контракт: /solo живет в каноне и зовет `claude-rc` как CLI; роль приезжает по имени, контент замораживается снапшотом в `role/` агента (recovery не зависит от текущего состояния канона); control не знает о правилах, toolkit - о tmux/systemd.

## Риски и грабли

1. **Permission prompts.** Безлюдная сессия на запросе разрешения молча висит. Митигция: pre-flight в /solo; для event - явный `--allowedTools`; у каждого агента свой settings-файл (модель доверия, п.5).
2. **Ресурсы VM.** 2 vCPU / 3.8 GB. Замеры спайка 2026-07-11: headless-прогон - пик ~0.29 GB, интерактивная сессия idle - ~0.43 GB (дерево процессов). Бюджет: система ~0.4 + control ~0.43 -> на агентов ~2.5-2.9 GB => **admission cap стартово 4 живых mission-агента** (+запас на рабочие пики и headless-прогоны). Сверх капа - очередь, control-plane в приоритете. Следующая ступень 4/8. Ресайз = перезагрузка = запертый LUKS.
3. **LUKS /data.** Инфраструктура - на корневом диске; чекауты - на /data. Проверка доступности - **fail-closed по факту смонтированности** (findmnt/device), не по существованию каталога: иначе агент напишет чекаут в пустой каталог на root FS, и mount его скроет. При запертом /data - один алерт, агенты не поднимаются.
4. **Лимиты подписки.** Event-пул - отдельный недельный; расход пишется инкрементально (не только финальный JSON - kill его теряет), капы этапа 4 останавливают, а не только показывают.
5. **Prompt-injection через события.** Граница - инструментальная, не текстовая: недоверенный вход = без Bash, без чувствительных MCP, suggest (модель доверия, п.2). Промпт-обертка "событие = данные" остается вторым эшелоном.
6. **Гонки владения.** Lease в control.json (владелец, generation, TTL); захват = kill старого -> acquire -> generation++; записи под flock через helper; stale-записи отсекаются по generation в state.json.
7. **Незавершаемость миссий.** Стоп-условия в spec; reconciler меряет max_hours своими часами (started_at в control.json), виток - по iteration_started_at; превышение = interrupt + карантин needs-attention + пуш.
8. **Недетерминированное восстановление.** Идемпотентный проход reconciler'а с retry/backoff; N неудач - needs-attention, не вечные рестарты; staggered resume после массового падения.
9. **Побочные эффекты не откатываются.** act - только в ветке/worktree; внешние необратимые действия - см. "Модель доверия", п.4.
10. **Диск и чувствительное на нешифрованном корне.** inbox, events.jsonl, dead-letter - под ретеншн/logrotate с первых дней. Транскрипты сессий (`~/.claude/projects`) и логи `sessions/` живут на корне вне LUKS - reconciler чистит старше N дней: это и место (root FS 50G), и сокращение объема данных, читаемых из снапшота диска. OAuth-токены на корне - осознанно (иначе парк не переживает ребут); компенсация - права 600 и отзываемость.
11. **Хрупкий старт claude-сессии (модальные экраны).** Сброс/релокация `.claude.json` (например смена CLAUDE_CONFIG_DIR - переменная перемещает `.claude.json` внутрь своего каталога) обнуляет онбординг/тему/**trust для cwd** -> безлюдная сессия виснет на setup/trust-экране, не коннектясь к relay. Тест-ребут 2026-07-11: control-сессия молча простояла ~15 мин, живой процесс маскировал отключку. Митигация: обертка `claude-control-session` перед стартом идемпотентно **пресидит** для своего cwd `projects["<cwd>"].hasTrustDialogAccepted=true` + `hasCompletedOnboarding`/`theme` в актуальном `$CLAUDE_CONFIG_DIR/.claude.json`; reconciler трактует "живой процесс без свежего heartbeat" как needs-attention (чек-лист 1a, "живость = коннект к relay").
