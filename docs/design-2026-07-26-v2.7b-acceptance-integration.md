# V2.7b: приемка, интеграция, уборка, архив

Вторая половина V2.7 (первая - `design-2026-07-26-v2.7a-task-birth-and-done.md`). V2.7a доводит задачу до заявки о готовности: `done.json` в состоянии `requested` с зафиксированными `branch`/`base`/`commit_sha`/`empty` (worktree) или `changes` (direct), и карточка об этом уходит в TG. Здесь - все, что после: вердикт человека, интеграция результата, уборка и архив.

Наследуется без изменений: `done.json` пишется только под `done.lock`; поля `accepted_at`/`integrated_at`/`cleaned_at`/`archived_at` уже зарезервированы схемой (`bin/claude-agent-done:85-88`) и до сих пор всегда `null`; `claude-agent-done` отказывается переоткрывать заявку, если `state` вне `(None, "requested")` - это и есть защита от того, чтобы агент переписал уже вынесенный вердикт.

**Не путать с `acceptance.status` в `control.json`** (`bin/claude-agent-reconciler:1002-1027`, stage7, `design-2026-07-12-stage7-acceptor-role.md`). Это другой, более старый механизм: авто/LLM-вердикт по артефакту миссии. Наша FSM живет в поле `state` файла `done.json` и с ним не пересекается. Совпадение слов "accept" в двух машинах - главная ловушка при чтении кода этого этапа.

## 1. Схема `projects.yaml` и обратная совместимость

Сегодня файл - плоская карта `<name>: <path>`, и она читается шестью местами одним и тем же выражением `yq -r '.[strenv(name)] // ""'`: `bin/claude-rc:232,256,348,420,476,541`, `bin/claude-rc-agent:552-557`, `bin/claude-control-project-watchdog:133-136`. Ни одно из них не лезет во вложенное поле, поэтому подстановка объекта вместо скаляра не даст ошибки - yq вернет сериализованную мапу, и путь к проекту молча превратится в мусор. Это отказ класса "проверка, которая не может провалиться": ломается не там, где меняли.

Обе формы валидны и обязаны сосуществовать:

```yaml
claude-control: /data/git/claude-control          # форма A, как сейчас
проект 1:                                           # форма B
  path: /data/git/проект 3
  integrate: pr
```

1. **Один резолвер на весь репозиторий.** Заводится `bin/_rc_projects.sh` - sourced-хелпер с двумя функциями: `project_path <name>` и `project_integrate <name>`. Все шесть мест выше переводятся на `project_path`. Дублировать yq-выражение по файлам запрещено: именно расхождение копий и есть тот дрейф, который этот пункт закрывает. Питоновской стороне (`bin/claude-agent-run`, фаза интеграции) хелпер тоже нужен, а sourced-файл она не подхватит - она зовет его подпроцессом (`sh -c '. <helper>; project_path "$1"' _ <name>`), а не заводит вторую копию выражения на питоне. Имя проекта берется из `spec.yaml` агента (`.project`).
2. `project_path` принимает обе формы: скаляр отдается как есть, мапа - через `.path`. Мапа без `path` - пустой ответ (для вызывающего это "проект не зарегистрирован", поведение как сегодня).
3. `project_integrate` отдает `.integrate` для формы B и пустую строку для формы A.
4. **Дефолт - `none`**, и он безопасный: результат не вливается автоматически никуда, ветка остается на месте, dwl вливает руками. Форма A (все нынешние проекты) получает именно его, поэтому раскатка этапа сама по себе ничего не сливает в main.
5. Значение `integrate` вне `merge|pr|none` - **отказ фазы интеграции** с attention, а не тихий дефолт. Опечатка в конфиге не должна вырождаться в "ничего не делаем и рапортуем успех".
6. **Ключ реестра фиксируется при create.** В `spec.yaml` поле `.project` хранит уже разрезолвленный путь, а не имя из `projects.yaml`, поэтому восстанавливать имя обратным поиском по пути запрещено: два имени могут указывать на один путь, а путь может вообще выпасть из реестра, и режим интеграции тогда молча выродится в дефолт. Имя фиксируется в `control.json` как `project_name` в момент create, когда реестр заведомо свежий: `cmd_create` резолвит его по пути, а `cmd_new_task` следом перезаписывает точным значением из аргумента (он-то знает имя достоверно, и это снимает неоднозначность "два имени - один путь"). Фаза интеграции только читает готовое поле. Резолв на create нужен потому, что агента заводят и напрямую, минуя `new-task`, - без него такие агенты остались бы вообще без `project_name`.
7. **Деплой.** `install.sh` копирует в `~/.local/bin` явный список файлов (`install.sh:223-233`), и `_rc_projects.sh` обязан быть в нем. Без этого раскатка кладет `claude-rc`, `claude-rc-agent` и watchdog разом: они делают `source` соседнего файла, которого в целевом каталоге не окажется.

## 2. FSM в `done.json`

```
requested --вердикт "принять"--> accepted --фаза integrate--> integrated
         \                                                        |
          --вердикт "отклонить"--> rejected --фаза revise--> (файл снят)
                                                                  |
                                            cleaned <--фаза cleanup
                                               |
                                               +--фаза archive--> archived
```

Поля, дописываемые к схеме V2.7a: `verdict_at`, `verdict_by`, `verdict_comment`, `integrate_mode`, `integrate_ref` (merge-коммит или URL PR), `phase_attempts`, `phase_error`.

Правила, общие для всех фаз:

- **Владелец записи один** - подкоманда `claude-agent-run done-advance <agent_dir>`. Реконсилер зовет ее безусловно на каждом проходе, рядом с существующими `question-reminders` и `done-notify` (`bin/claude-agent-reconciler:1255-1258`) - тот же шов, та же дисциплина: подкоманда сама берет `done.lock` и сама решает, что делать нечего.
- **Одна фаза за вызов.** Проход не пытается прогнать всю цепочку: сдвинул состояние на один шаг - вышел. Так каждая фаза наблюдаема отдельно, а крах уносит максимум один шаг.
- **Идемпотентность и переисполнимость.** Любая фаза, прерванная в середине, доигрывается со следующего тика из последнего записанного состояния, без повторных внешних эффектов (второй PR не создается, второй мерж не делается).
- **Переход пишется последним.** Внешний эффект (мерж, push, rename) выполняется до записи нового `state`; повторный проход обязан распознать уже сделанный эффект и не повторить его. Обратный порядок дал бы потерю: состояние продвинуто, эффекта нет.
- Коды возврата `done-advance`: `0` - продвинулись или делать нечего; `3` - фаза не удалась и это записано в `phase_error`; `2` - ошибка вызова/внутренняя. Молчаливого `0` на провале быть не должно - на этом уже обжигались в V2.6.
- **Attention - тот же флаг, что у реконсилера, и снимается только свой.** Поле одно на всех: `control.json.attention`, пишется через `claude-agent-io control-cas` - тем же механизмом, что `set_attention`/`clear_attention` в `bin/claude-agent-reconciler:163,171`. Пишет его сама фаза (`done-advance` зовется и реконсилером на каждом тике, и напрямую, и привязывать появление флага к тому, кто позвал, неправильно), с `reason: "done_phase"`. **Снятие обязано быть с `--expect attention.reason="done_phase"`**: без этой сверки удачно прошедшая фаза погасила бы внимание, поставленное совсем по другому поводу. Не путать с `acceptance.status` - вот это действительно чужая машина stage7, а `attention` общий.
- Коды возврата `done-verdict`: `0` - вердикт применен либо это повторный тап по уже вынесенному (no-op); `3` - карточка устарела, вердикт не применен; `2` - ошибка вызова. Классификация "применили / уже было / устарело" целиком принадлежит этой подкоманде, потому что только она держит `done.lock`; вызывающий получает исход машиночитаемой строкой в stdout (`applied` / `already` / `stale`).

## 3. Вердикт: карточка, кнопки, доверие

Карточка готовности сегодня уходит обычным текстом: `question_card` возвращает `(None, None)` для всего, кроме `kind == "question"` (`bin/claude-agent-tgbot:265-315`). Добавляется ветка `kind == "done"` - тот же чистый seam, что и в V2.5: функция строит `(text, reply_markup)` и ничего не отправляет.

1. Кнопки - две: "принять" и "отклонить". Callback-data: `d:<agent>:<sha8>:a` и `d:<agent>:<sha8>:r`, где `sha8` - первые 8 символов `commit_sha` из заявки (для `direct`/`none` - `-`). Префикс `d:` свободен, занятые - `q:`, `p:`, `r:`, `m:` (`bin/claude-agent-tgbot:297-315`).
2. **`sha8` в callback-data - не украшение, а проверка на устаревание.** Агент мог передекларировать готовность с новым коммитом (V2.7a это разрешает: продвинувшийся `commit_sha` пересобирает заявку), и тогда карточка в чате описывает не то, что лежит в `done.json`. Тап по такой карточке обязан быть отклонен с "устарело", а не применен к новому коммиту, - dwl принимал глазами конкретный результат.
3. **Доверие - как в V2.5: право писать, а не поле в полезной нагрузке.** Бот не трогает `done.json` вообще - ни на запись, ни на чтение. Он вызывает `claude-agent-run done-verdict <dir> --accept|--reject [--comment T] --expect-sha <sha8>` и показывает человеку то, что вернула подкоманда. Читать файл ради собственной проверки "не устарело ли" нельзя: между чтением и вызовом состояние меняется, и получаются две стороны, каждая из которых считает, что проверяет она. Проверка одна, под локом, внутри `done-verdict`. Личность отправителя проверяется до вызова (тот же гейт chat_id, что у `/new`).
4. Повторный тап - no-op: `verdict_at` не переписывается, вторая карточка не шлется. Тап по уже обработанной карточке отвечает "уже принято"/"уже отклонено".
5. **Вердикт неизменяем: кто первый, тот и записан.** Отклонить можно двумя путями - тапом по кнопке (без комментария) или reply-ответом на карточку (механика V2.5 уже есть), и тогда текст ответа идет в `verdict_comment`. Что пришло первым, то и вердикт; все последующее - no-op с ответом "уже отклонено", в том числе reply после тапа. Дописывать комментарий к уже вынесенному вердикту нельзя: это запись поверх решения, которое контур мог уже унести в работу. В тексте карточки прямо сказано, что для отказа с объяснением надо отвечать сообщением, а не жать кнопку.

## 4. Фаза integrate

Выполняется в состоянии `accepted`. Режим - `project_integrate` (§1).

**Фенсинг перед любым действием.** Между `requested` и интеграцией проходит время, за которое ветка задачи могла уехать. Поэтому фаза заново читает `git rev-parse refs/heads/<branch>` и сверяет с `commit_sha`, записанным в заявке. Расхождение - отказ с attention, интеграции нет. Проверка обязана быть провалимой: тест B14 двигает ветку после заявки и требует именно отказа. (Ровно этот класс ошибки поймал аудит V2.7a, где база выводилась из HEAD и родство становилось тавтологией.)

`empty: true` - интегрировать нечего: фаза сразу пишет `integrated` с `integrate_ref: null`, `integrate_mode: "skipped"`.

**`integrate: none`** - тоже `integrated`/`skipped`, ветка и ее коммиты остаются на месте. Это дефолт, и он ничего не разрушает.

**`integrate: merge`.** Целевая ветка обязана быть известна явно: `cmd_create` начинает писать в `control.json` рядом с `mission_base` еще и `mission_base_branch` (символическое имя ветки на момент create; detached HEAD - пустое). Выводить цель на лету нельзя - dwl мог за это время перейти на другую ветку, и результат уехал бы не туда. Агенты, созданные до этого этапа, поля не имеют: для них merge - **отказ** с внятным текстом "база не зафиксирована, влей вручную", а не догадка.

Порядок:

1. Если целевая ветка где-либо вычекаучена и дерево там грязное - отказ, ничего не трогаем. Чужую работу контур не двигает.
2. Если тип задачи - потомок текущего конца целевой ветки, это перемотка: `git update-ref refs/heads/<base_branch> <commit_sha> <old_sha>`. Старое значение передается третьим аргументом обязательно - это CAS, без него параллельное движение ветки затирается.
3. Иначе - настоящий мерж, но **не в рабочем дереве dwl**: контур создает временный `git worktree add --detach`, мержит там, и только при успехе переставляет ссылку тем же CAS-обновлением. Временный worktree снимается в любом исходе, включая крах.
4. Конфликт - `git merge --abort`, временный worktree убран, attention плюс карточка "нужен ручной мерж". Состояние остается `accepted`: dwl разруливает, следующий тик доигрывает. Автоматического разрешения конфликтов нет и не планируется.
5. `integrate_ref` = получившийся sha целевой ветки.

**`integrate: pr`.** Push ветки в `origin`, затем `gh pr create`. Идемпотентность - по факту существования PR для этой головы (`gh pr list --head <branch>`): нашелся - переиспользуется, второй не создается. Отсутствие `gh`, отказ push или ошибка API - `phase_error` плюс attention, состояние остается `accepted`, следующий тик пробует снова. Push делает контур, не агент: у агента нет и не должно быть прав на удаленный репозиторий.

## 5. Фаза cleanup

Выполняется в состоянии `integrated`. Снимает ровно то, что поставил create, - симметрично EXIT-ловушке `bin/claude-rc-agent:269,490`, которая уже умеет откатывать создание.

- `workspace: direct` и `none` - делать нечего, сразу `cleaned`.
- `worktree`: дерево обязано быть чистым. Грязное - отказ с attention (там несохраненная работа), `--force` не используется никогда.
- `git worktree remove <agent_dir>/work` плюс `git worktree prune`.
- Ветка удаляется **только при `integrate: merge`** и только после подтверждения, что коммит содержится в целевой ветке. При `pr` ветка нужна живому PR, при `none` - это единственное место, где лежит результат. Удалить ее там значило бы уничтожить работу, которую человек только что принял.

## 6. Фаза archive и надгробие

Выполняется в состоянии `cleaned`.

1. Архивировать бегущего агента нельзя: если юнит активен или `desired` не `stopped` - фаза сначала гасит его штатным путем и выходит; архив случится следующим тиком.
2. `os.rename(agents/<name>, archive/<name>-<archived_at>)` - атомарно, оба каталога под одним корнем, значит на одной ФС. `archive/` и `tombstones/` лежат рядом с `agents/`, то есть в `dirname(AGENTS_DIR)`.
3. **Надгробие обязательно.** `/new` идемпотентен по имени задачи, производному от `update_id` (V2.7a §1): после архива имя снова свободно, и переотправленный Telegram-ом старый апдейт заведет вторую задачу с той же постановкой. Пишется `tombstones/<name>.json` (имя, когда архивировано, куда), `cmd_new_task` сверяется с ним до create и отвечает "задача уже завершена". TTL надгробия - 30 суток, чистится тем же проходом; окно переотправки Telegram много меньше.

## 7. Путь отказа

Вердикт "отклонить" пишет `state: "rejected"` плюс `verdict_comment`. Дальше фаза `revise`, тремя переисполнимыми шагами строго в этом порядке:

1. Дописать текущий документ в `done.history.jsonl` (пропустить, если последняя строка уже с этим `verdict_at`).
2. Положить в spool событие-доработку с комментарием, `--id rev:<name>:<verdict_at>` - дедуп при повторе.
3. Снять `done.json`.

Крах между шагами безопасен: история не задвоится по ключу, событие - по `--id`, а снятие файла идемпотентно по своей природе. После снятия `claude-agent-done` снова видит отсутствие файла и разрешает свежую заявку - специально: отклоненная задача обязана иметь возможность доделаться и предъявиться заново. Ничего в V2.7a для этого менять не нужно, там уже `state in (None, "requested")`.

## 8. Отказы, внимание, изоляция

- Любая неудавшаяся фаза: `phase_attempts += 1`, текст в `phase_error`, attention на агенте, состояние **не** двигается.
- Карточка об ошибке не спамит: одинаковая подпись ошибки шлется один раз, повтор только при смене подписи или после успеха. Тик реконсилера - каждые пол-минуты, без этого чат превратится в лог.
- **Бульхед.** Падение фазы у одного агента не должно ронять проход по остальным - урок V2.6. Нечитаемый или битый `done.json` - attention по этому агенту и продолжение прохода, а не исключение наружу.
- Отсутствие проекта в `projects.yaml` на момент интеграции (переименовали, убрали) - отказ фазы с внятным текстом, не молчаливый пропуск.

## 9. Швы

Аудиты семи предыдущих этапов дали устойчивый вывод: тесты закрепляют ошибку контракта, а не находят ее, и слепы к стыкам, где каждая сторона мокает другую. Поэтому здесь заранее прибиты три места, которые обязаны проверяться настоящим кодом обеих сторон:

1. Кнопка приемки идет через **реальный** `route_callback` бота (как N16 в V2.7a), а не через фикстуру с руками собранным callback-data. Именно на этом шве в V2.6 и V2.7a нашлись блокеры: подсистема была рабочей, а телефонная половина - нет.
2. Мерж и перемотка проверяются на **настоящих** git-репозиториях, фикстурой `mk_worktree_agent()` (`tests/test-agent-task-lifecycle.sh:120`), которая поднимает агента через настоящий `agent create`. Мок git тут бессмыслен - вся суть фазы в его поведении.
3. Проверка "коммит не уехал" и проверка "целевая ветка зафиксирована" обязаны иметь тест, где они **проваливаются**. Проверка, которая не может провалиться, - главный повторяющийся дефект этой серии этапов.

## 10. Тесты

Суита - `tests/test-agent-task-lifecycle.sh` (продолжение нумерации V2.7a), фикстуры и каркас те же (`mk_worktree_agent` :120, `mk_none_agent` :143, `write_done_json` :183, `mk_alert_ok`/`mk_alert_fail` :218/:227).

**Схема проекта.** B1 плоская форма читается всеми шестью местами как раньше. B2 объектная форма отдает `path`. B3 объектная без `integrate` - дефолт `none`. B4 незнакомое `integrate` - отказ фазы плюс attention, состояние на месте. B5 структурный: вне `bin/_rc_projects.sh` yq-выражения резолва нет ни разу (внутри самого хелпера их закономерно два - путь и режим, это не дубль). B5a структурный: `_rc_projects.sh` присутствует в списке копируемого в `install.sh`.

**Вердикт.** B6 тап "принять" проходит через реальный `route_callback`. B7 тап с чужого chat_id игнорируется, состояние не движется. B8 повторный тап - no-op, `verdict_at` не переписан. B9 карточка с устаревшим `sha8` (агент передекларировал) - "устарело", вердикт не применен. B10 структурный: бот не открывает `done.json` ни на чтение, ни на запись (проверяется по факту обращения к файлу, а не по наличию строки в тексте - упоминание в комментарии безобидно). B11 комментарий из reply попадает в `verdict_comment`.

**Интеграция.** B12 merge-перемотка двигает целевую ветку, `update-ref` вызван с проверкой старого значения. B13 целевая ветка ушла вперед без конфликта - мерж во временном worktree, рабочее дерево dwl не тронуто, временный убран. B14 ветка задачи сдвинулась после заявки - отказ, мержа нет. B15 нет `mission_base_branch` (агент старого образца) - отказ с внятным текстом. B16 целевая ветка вычекаучена с грязным деревом - отказ, ничего не тронуто. B17 конфликт - abort, временный worktree снят, attention, состояние `accepted`. B18 `empty: true` - сразу `integrated`/`skipped`. B19 `integrate: none` - `skipped`, ветка цела. B20 pr: push плюс создание PR, url записан. B21 pr: PR уже существует - переиспользован. B22 pr: push упал - `accepted`, attention, следующий тик повторяет.

**Уборка и архив.** B23 worktree снят, prune выполнен, ветка удалена при `merge`. B24 при `pr` и `none` ветка сохранена. B25 грязный worktree - отказ, `--force` не применяется. B26 `direct`/`none` - no-op. B27 бегущий агент не архивируется, гасится и уходит на следующий тик. B28 архив - атомарный rename в `archive/`, надгробие создано. B29 `/new` с именем из надгробия не заводит дубль.

**Отказ.** B30 reject: история дописана, событие-доработка в spool, `done.json` снят. B31 повторный reject - no-op. B32 крах между шагами revise - событие не задвоилось (дедуп по `--id`), история не задвоилась. B33 после снятия файла агент может заявить готовность заново.

**Живучесть.** B34 крах в каждой фазе - следующий тик доигрывает с последнего записанного состояния, без повторных внешних эффектов. B35 бульхед: провал фазы у агента A не мешает агенту B. B36 нечитаемый `done.json` - attention, проход продолжается. B37 одна фаза за вызов: из `accepted` один вызов доводит ровно до `integrated`. B38 одинаковая ошибка не шлет вторую карточку.

## 11. Что не входит

Автоматическое разрешение merge-конфликтов; ревью содержимого диффа (это V2.9 и роль ревьюера stage7, отдельная машина); удаление архивов старше срока; веб-панель. Переименование проекта - решение отложено до конца V2.7, к контракту отношения не имеет.
