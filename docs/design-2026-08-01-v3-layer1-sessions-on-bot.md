# V3.0 - слой 1 переезжает в бота

Контракт этапа. Слой 1 ("remote-control диспетчер": вечная control-сессия + `claude-rc` + tmux) заменяется управлением из Telegram-бота: меню проектов -> меню сессий по их собственным именам -> поднять/положить. Работа после подъема идет в приложении Claude Code, как и раньше.

## 1. Почему сейчас

Решение 2026-07-25 сняло восстановление прошлой сессии в мост с целей, зафиксировав констрейнт "не переоткрывать":

> Resume прошлой сессии в мост не вытягивается: сессии кончаются на deferred-tool -> `No deferred tool marker` -> exit. `--resume` и `--fork-session` не спасли.

**Констрейнт опровергнут 2026-08-01.** Не хватало двух вещей, ни одна из которых не про resume:

1. **промпт** - ошибка говорит об этом прямым текстом ("Provide a prompt to continue the conversation"), без него CLI выходит ВСЕГДА, а не только на прерванной сессии;
2. **pty** - без tty процесс отрабатывает промпт как одноразовый запуск и завершается, к мосту не подключившись (сокетов 0).

Рабочая форма проверена на двух живых сессиях: `script -qec "claude --remote-control <имя> --resume <uuid> --debug-file <лог> '<промпт>'"`. Обе зарегистрировались в мосту и были видны с телефона.

Отсюда же закрывается открытый вопрос №3 того решения ("судьба session-части `claude-rc`"): она переезжает в бота.

## 2. Что удаляется

- `claude-control-session` (вечная control-сессия) и юнит `claude-control.service`;
- `claude-control-watchdog` + таймер: сторожить больше нечего;
- `control-CLAUDE.md.example` и роль "диспетчер, понимающий 'подними X'";
- tmux как держатель сессий.

Мотив не только в дублировании: control-сессия держала 172 МБ постоянно, замерзала раз в 3-5 дней (по `watchdog.log`: 11.07, 17.07, 25.07 дважды, 29.07) и была самым хрупким звеном контура. Ее единственная задача - превратить фразу в вызов `claude-rc` - у бота решается кнопкой, без LLM в data-plane.

## 3. Держатель сессии - транзиентный systemd-юнит

Решение dwl 2026-08-01: не tmux, а тот же механизм, что у агентного слоя.

```
systemd-run --user --unit ccsession-<uuid8> --service-type=exec \
  --property=KillMode=control-group --property=MemoryMax=<N>M \
  --setenv PATH=... --setenv CLAUDE_CONFIG_DIR=... \
  script -qec "claude --remote-control <name> --resume <uuid> --debug-file <dbg> '<prompt>'" <log>
```

- `script -qec` внутри юнита дает pty (§1, пункт 2). Юнит - Type=exec, чтобы старт означал именно запуск процесса;
- `KillMode=control-group` - гашение забирает и `script`, и `claude`;
- `MemoryMax` - сессия весит ~450 МБ, потолок держит хост от OOM (машина 12 ГБ, инцидент в анамнезе);
- имя юнита выводится из **полного** uuid сессии (без дефисов), а не из имени проекта: сессий одного проекта может быть поднято несколько, а префикса в 8 символов мало - две сессии с общим началом делили бы live-состояние, `down` и файлы логов.

Что теряется против tmux: `tmux attach` с машины. Замена - `journalctl --user -u ccsession-<uuid8>` и файл лога; интерактивный attach к сессии с хоста больше не поддерживается (работа идет с телефона или из Cursor).

## 4. Имя сессии

Имя в `--name` = собственное название сессии (`custom-title`, то же, что видно в Cursor). Правило и его причина - `docs/architecture.md`, раздел про `claude-rc`; фикс сделан 2026-08-01 (`401bf78`). **Имени нет - `--name` не передается вовсе:** проверено пробой, что без этого флага CLI не пишет ни `custom-title`, ни `agent-name`, и сессия остается безымянной. Подставить сюда имя проекта нельзя - оно осело бы в `custom-title` намертво, и все безымянные сессии проекта получили бы одинаковое клеймо.

Переименование по ходу работы (`/rename`) уходит в мост вживую (`[bridge] Session title updated successfully`), так что имя карточки на телефоне остается синхронным без участия контура.

## 5. Протокол CLI (то, что зовет бот)

| Глагол | Назначение |
| --- | --- |
| `claude-rc sessions <project> --porcelain` | TSV сессий: `uuid \t mtime \t origin \t cwd \t title \t live` |
| `claude-rc up <project> <uuid> [--prompt TEXT]` | поднять сессию транзиентным юнитом |
| `claude-rc down <uuid>` | погасить (SIGTERM юниту, дренаж, затем stop) |
| `claude-rc live` | имена поднятых юнитов, по одному в строке |

Требования к `--porcelain`: одна строка на сессию, поля разделены табом, значения санитизированы до одной печатной строки (title приходит из транскрипта и остается **недоверенными данными**), сортировка от свежих.

`up` идемпотентен: юнит для этого uuid уже активен - no-op с сообщением, а не второй экземпляр.

Промпт по умолчанию нейтральный ("на связи, жду задачу"); он обязателен по §1, но не должен провоцировать действия - сессии поддержки клиентов идут с широкими правами.

## 6. Экран бота

`/sessions` -> инлайн-кнопки проектов из `projects.yaml` -> кнопки сессий: `● <title> · <возраст>` (кружок = поднята) -> действия `Поднять` / `Положить` / `Назад`.

- авторизация - существующая (приватный чат + whitelist по `from.id`), отдельного гейта не вводим;
- callback-данные несут `project` и `uuid`; оба валидируются до вызова CLI (проект - по `projects.yaml`, uuid - по формату), текст из транскрипта в callback не попадает;
- title в кнопке эскейпится как недоверенные данные, как и остальной вывод агентов.

## 8. Миграция

1. Раскатать новые глаголы и экран бота, обкатать на одной сессии.
2. Снять `claude-control.service` и `claude-control-watchdog.timer` (решение dwl: сразу вместе со слоем 1), убрать их из `install.sh`/`uninstall.sh` и из README/architecture.
3. `project-watchdog` снят вместе с control-сессией: он сторожил tmux-окна, которых больше нет. Надзора за `ccsession-*` пока НЕТ - зависшая сессия лечится тапом "положить"/"поднять" в боте. Это осознанный размен: автоперезапуск сессии, которую человек поднимает по требованию, ценит меньше, чем лишний сторож в контуре. Юнит-файлы control-сессии и обоих watchdog'ов установщик по-прежнему кладет на диск (для отката), но больше не включает и снимает с уже установленных машин.

Остаток: `~/.claude-control/sessions/*.log` продолжает наполняться, ротация уже покрыта `claude-control-logrotate`.
