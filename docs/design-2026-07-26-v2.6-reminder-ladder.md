# V2.6: лестница напоминаний

Контракт этапа (SDD). Замыкает цикл с телефона: V2.5 дал карточку и обратный путь ответа, здесь появляется **доставка** - единственный владелец пушей по вопросам.

## Цель

Вопрос, оставшийся без ответа, не тонет. Первая карточка уходит почти сразу после того, как прогон задал вопрос, дальше напоминания идут разреженной лесенкой - настойчиво, но не назойливо. Ответил, отложил, вопрос закрылся - напоминания прекращаются.

## 1. Единственный владелец

Пуши по вопросам целиком принадлежат **reminder-контуру reconciler**. Ни runner, ни `claude-agent-ask`, ни хук подтверждений карточку не шлют - барьер зафиксирован тестом V2.5 T15 и снимать его нельзя (обоснование - V2.5 §2).

Существующий 6-часовой репуш обычных алертов (`do_alert` в `claude-agent-reconciler`) - **отдельный контур, не трогаем**. У напоминаний своя каденция, дедупу по 6 часов они не подчиняются.

## 2. Где живет решение: `claude-agent-run question-reminders <agent>`

Логика лесенки - в runner'е (python), а не в bash-контуре: файлы вопросов принадлежат ему, RMW под `questions/.lock` там уже есть, и это дает естественный тестовый шов. Reconciler на каждом тике (60 с) просто зовет подкоманду для каждого агента.

Подкоманда для каждого файла `questions/*.json` этого агента:

1. Пропустить, если `status != "open"`, либо `answered_at` непуст (ответ дан - напоминать не о чем), либо `now < snoozed_until`, либо `now < next_push_at`.
2. Отправить карточку: `CLAUDE_AGENT_ALERT_CMD <agent> <reason> <detail> <json-detail>`. Аргументы фиксированы:
   - `<agent>` - **короткое имя агента** (как в `do_alert`), не путь к каталогу;
   - `<reason>` - постоянная строка `вопрос ждет ответа`;
   - `<detail>` - `<qid>`. Текст вопроса сюда НЕ кладется: он идет в json-detail, который на TG-пути и рендерит карточку с редакцией. Аргументы 2-3 существуют для alert-команд, не умеющих в json-detail;
   - `<json-detail>` - detail из V2.5 §3 (`kind`, `agent`, `qid`, `qkind`, `text`, `options`).
3. **Ступень продвигается только после успешной доставки** (§4). Успех -> под `questions/.lock`: `step += 1`, `next_push_at = now + ladder[min(step-1, last)]`. Неуспех -> файл не меняется, та же ступень повторится на следующем тике.
4. Печатает построчно `<qid> <sent|skip|fail>` - для тестов и для лога reconciler.

**Код возврата подкоманды** - про саму подкоманду, а не про исход вопросов: 0, если она отработала (сколько бы `fail` ни было в строках), ненулевой - только на ошибке употребления (нет такого агента, кривые аргументы). Иначе reconciler получал бы красный статус на каждом сетевом сбое Telegram, а исход по каждому вопросу и так виден построчно.

Нечитаемый или битый файл вопроса - строка `<basename-без-.json> skip` и запись в лог, а не падение подкоманды: один сломанный файл не должен глушить напоминания по остальным.

**Переборка держит любой сломанный файл, а не только нечитаемый** (аудит V2.6, major): валидный JSON с испорченной схемой (`reminder: "x"`, `step: "0"`) ронял обработку остальных вопросов, а в случае `step: "0"` - уже ПОСЛЕ отправки, из-за чего карточка уходила заново каждый тик бессрочно. Тело обработки одного вопроса целиком под `try/except`: любое исключение -> `skip` по этому вопросу и переход к следующему.

**Пересчет решения под локом** (аудит V2.6, major): сегодня вопрос читается и проверяется без лока, потом идет доставка, и только потом `questions_rmw` берет лок и продвигает ступень, не перепроверяя ничего. Между чтением и записью успевают ответ, снуз и закрытие вопроса - ступень продвигается не с той ступени, а параллельные вызовы продвигают ее дважды. Сетевую отправку под локом держать нельзя, поэтому правило такое: **решение о ступени принимается заново внутри мутатора** - если к моменту записи `status != open`, появился `answered_at`, изменился `step` или выставлен `snoozed_until` в будущем, ступень НЕ двигается. Сама карточка при этом может уйти вдогонку уже отвеченному вопросу - это неизбежно (сеть не атомарна с состоянием) и безобидно: тап по ней вернет "устарело".

Дополнительно весь проход `question-reminders` по агенту идет под `questions/.reminders.lock` (неблокирующий захват; занято -> подкоманда молча выходит с 0): два тика reconciler внахлест не должны слать по карточке каждый.

**Недоступный `questions/` - громкий отказ, а не пустота** (аудит V2.6, major): `OSError` на `listdir` (например `EACCES`) молча давал exit 0, то есть навсегда и неотличимо выключал напоминания агента. Теперь - строка в лог и ненулевой код возврата: это ошибка употребления, а не "вопросов нет".

**Транспорт лег - не блокируем reconciler** (аудит V2.6, major): напоминания вызываются синхронно внутри прохода admission, и при зависшем канале каждый агент с висящим вопросом добавляет до 30 с задержки lease/recovery. Поэтому таймаут доставки - 10 с, и **первый же `fail` в проходе прекращает попытки**: остальные вопросы получают `skip` (ступень не двигается, повтор будет на следующем тике). Канал лежит - это состояние канала, а не N независимых поводов ждать.

**Лишние аргументы - ошибка** (аудит V2.6, minor): подкоманда принимает ровно один позиционный аргумент; мусор после него -> ненулевой код, а не молчаливое игнорирование.

`CLAUDE_AGENT_ALERT_CMD` не задан -> контур не делает ничего (ступень не двигается, спама в лог нет).

**Позиция json-detail - четвертая, и это надо проверять сквозным тестом** (аудит V2.6, blocker). `mode_send` разбирал JSON из **третьего** аргумента, а `alert_question` кладет туда `qid` - в результате боевой question-путь не включался никогда: `json.loads(qid)` падал, карточка вырождалась в обычный текстовый алерт без кнопок и без записи в `sent_map`, код возврата приходил нулевой, и лестница исправно продвигала ступень, будто карточка доставлена. Ни одна суита этого не ловила: тесты V2.5 бьют по `question_card` и по `mode_send` со своей сигнатурой, тесты V2.6 - по мок-скрипту вместо реального бота. **Стык двух этапов не покрывал никто.** Кейс R15: взять argv ровно в том виде, в каком его формирует `alert_question`, и скормить настоящему `mode_send`.

**Отсутствие конфигурации Telegram - не доставка** (аудит V2.6, major): `mode_send` выходил с нулем еще до разбора аргументов при пустом токене или whitelist. На question-пути это ложный успех и продвижение ступени в никуда; на обычном пути нулевой код остается (регресс).

**Переменная обязана указывать на один исполняемый файл**, а не на команду с аргументом: и reconciler, и runner подставляют ее как argv[0] целиком, поэтому значение `claude-agent-tgbot send` не работает. Боевая связка - тонкая обертка `examples/claude-agent-tgbot-hook` (`exec ... send "$@"`): `"$@"` доносит четвертый аргумент, `exec` сохраняет код возврата, на котором держится §4. Обертка живет в репозитории именно потому, что без нее восстановление из репо оставляет `CLAUDE_AGENT_ALERT_CMD` указывающим в пустоту - и все пуши, включая карточки вопросов, умирают молча.

## 3. Лесенка

Ступени: **+15 мин -> +1 ч -> +4 ч -> +24 ч**, дальше сутки повторяются бессрочно. Верхнего предела и "сдачи" нет: незакрытый вопрос морозит цепочку задачи, поэтому забыть о нем система не имеет права.

- `create_question` (V2.3) уже ставит `next_push_at = asked_at`, поэтому **первая карточка уходит на ближайшем тике** - в пределах минуты после вопроса.
- `step` считает **успешные доставки**, а не тики.
- Переопределение для тестов: `CLAUDE_AGENT_REMINDER_LADDER_S` - список секунд через запятую (`"1,2,4,8"`). Пустое/битое значение -> боевая лесенка. **Битое = в том числе семантически** (аудит V2.6, major): ноль и отрицательные числа проходили `int()` как валидные, и при `-1` следующий срок оказывался в прошлом - вопрос спамился каждые 60 с вместо фолбэка. Все значения обязаны быть строго положительными, иначе - боевая лесенка целиком.

## 4. Честный код возврата доставки

Сегодня `mode_send` глотает исключения Telegram и всегда выходит 0 (`tgbot:739-747`) - на таком контракте "продвигать ступень только после доставки" невыполнимо: недоставленная карточка выглядела бы отправленной, и напоминание не повторилось бы никогда.

- **Question-путь** (`mode_send` с четвертым аргументом): успех = карточку принял **хотя бы один** получатель из whitelist. Ни одного -> ненулевой код возврата.
- **Обычные алерты** (без четвертого аргумента): поведение и код возврата **не меняются** - существующий вызов в `do_alert` идет с `|| true`, и трогать его в этом этапе незачем.

## 5. Снуз

Кнопка "напомнить позже" появляется на карточке вопроса (в V2.5 намеренно отложена сюда - там она была бы полем, которое никто не читает).

- `callback_data = "r:<qid>"`, роутинг - в `route_callback` рядом с `q:`/`p:`. Сама кнопка добавляется **внутри `question_card`**, а не постобработкой при отправке: чистая функция обязана возвращать то, что реально уйдет наружу, иначе ее тесты дают ложную уверенность о карточке. Кейсы V2.5 T3/T4 обновлены под лишнюю кнопку, T24 проверяет, что кнопка и маршрут не разъехались (callback_data берется из реальной карточки и скармливается роутеру).
- **Снуз абсолютный, не аддитивный:** `snoozed_until = now + 4 ч` (переустановка, не `+=`) - повторный тап и redelivery того же апдейта дают тот же результат. Длительность переопределяется для тестов через `CLAUDE_AGENT_SNOOZE_S` (секунды) - иначе проверить "после снуза лесенка продолжается с той же ступени" можно было бы только реальным четырехчасовым ожиданием.
- Снуз **не двигает** `step`: после паузы лесенка продолжается с той же ступени.
- Запись - через `claude-agent-run question-snooze <agent> --qid <qid>` (RMW под `questions/.lock`), бот зовет его после whitelist-проверки. Прямой записи в файл вопроса из бота нет.
- **`qid` обязан принадлежать нажатой карточке** (аудит V2.6, major). Сегодня сверка срабатывает, только если запись `sent_map` уже несет `qid`; любая старая запись без него (mission, legacy-алерт) позволяет подставить произвольный `r:<qid>` и снузить чужой вопрос того же агента, а повторными нажатиями - продлевать паузу бесконечно. Правило: для любого question-колбэка (`q:`/`p:`/`r:`) запись `sent_map` **обязана** нести `qid`, и он обязан совпасть; нет `qid` в записи -> "устарело", writer не зовется.
- Снуз на закрытый/отвеченный вопрос -> exit 2, состояние не меняется.

## 6. Дубль лучше пропажи

Контур падает между отправкой и записью ступени -> на следующем тике карточка уйдет повторно. Это принято осознанно: дубль напоминания безобиден (обе карточки ведут на один `qid`, тап по любой применяется один раз - V2.5 §7), а пропущенное напоминание означает молча зависшую задачу. Обратный порядок (сначала записать, потом слать) менял бы безобидный дубль на потерю.

## 7. Регресс-инварианты

- 6-часовой контур обычных алертов, `do_alert`, `alerts.jsonl` и дедуп по эпизодам - без изменений.
- `mode_send` без четвертого аргумента - текст, отсутствие клавиатуры и код возврата байт-в-байт.
- V2.3 FSM, V2.4 гейт, V2.5 роутинг и `sent_map` - не затрагиваются, кроме добавления кнопки снуза и ветки `r:`.
- Агент без открытых вопросов не порождает ни одного пуша и ни одной записи.

## 8. Тесты

Суита `tests/test-agent-reminders.sh` (bash, реальные файлы вопросов, alert-команда - мок-скрипт, пишущий argv в лог; сеть не нужна). Лесенка сжимается через `CLAUDE_AGENT_REMINDER_LADDER_S`.

- R1: открытый вопрос, `next_push_at` в прошлом -> ровно один вызов alert-команды с четвертым аргументом, `qid` совпадает; `step` стал 1, `next_push_at` сдвинут на первую ступень.
- R2: сразу повторный вызов подкоманды -> `skip`, второго пуша нет (`next_push_at` в будущем).
- R3: лесенка идет по ступеням - после N успешных доставок интервал соответствует N-й ступени; после последней ступени интервал держится на ней.
- R4: alert-команда вернула ненулевой код -> `fail`, `step` и `next_push_at` НЕ изменились, на следующем тике попытка повторяется.
- R5: вопрос с непустым `answered_at` -> `skip`, пуша нет.
- R6: закрытый вопрос -> `skip`, пуша нет.
- R7: снуз (с коротким `CLAUDE_AGENT_SNOOZE_S`) -> `snoozed_until` выставлен, пуша нет, пока не истечет; `step` не изменился; повторный снуз переустанавливает значение, а не накапливает; после истечения лесенка продолжается с ТОЙ ЖЕ ступени.
- R8: снуз на закрытый/отвеченный вопрос -> exit 2, файл не изменен.
- R9: битый JSON одного файла вопроса -> `skip` по нему, остальные вопросы того же агента обрабатываются.
- R10: `CLAUDE_AGENT_ALERT_CMD` не задан -> ни пушей, ни изменений файлов, код возврата 0, и в выводе строка `skip`, а не `fail` (аудит V2.6, minor: `fail` раз в тик на каждый вопрос засорял лог, хотя по §2 это полный no-op).
- R15 (blocker, сквозной стык): argv формируется ровно так, как его делает `alert_question`, и скармливается НАСТОЯЩЕМУ `mode_send` -> карточка распознана (текст с кнопками, запись в `sent_map`), json-detail взят из четвертого аргумента; при подмене четвертого аргумента мусором - обычный алерт и, на question-вызове, ненулевой код.
- R16 (major): пустой токен/whitelist -> question-вызов `mode_send` дает ненулевой код (ступень не двигается); обычный алерт при той же конфигурации по-прежнему дает 0.
- R17 (major): ответ/снуз/закрытие вопроса между чтением и записью -> ступень НЕ продвигается (пересчет в мутаторе); два одновременных прохода -> ровно один пуш и ровно одно продвижение.
- R18 (major): `reminder: "x"` и `step: "0"` -> `skip` по этому вопросу, остальные вопросы агента обработаны; в случае `step: "0"` повторная отправка на следующем тике не происходит бесконечно.
- R19 (major): `CLAUDE_AGENT_REMINDER_LADDER_S="-1"` и `"0"` -> фолбэк на боевую лесенку, а не срок в прошлом.
- R20 (major): `questions/` без прав на чтение -> ненулевой код и строка в логе, а не тихий 0.
- R21 (major): первый `fail` в проходе -> остальные due-вопросы получают `skip`, ступени не двигаются, проход не ждет по 30 с на каждом.
- R22 (major): снуз по карточке, чья запись в `sent_map` не несет `qid` -> "устарело", `question-snooze` не вызван.
- R23 (minor): лишний позиционный аргумент у `question-reminders` -> ненулевой код.
- R11 (регресс §7): `mode_send` **без** четвертого аргумента - текст, отсутствие клавиатуры и код возврата голден V2.5. Это и есть настоящий риск этапа: честный код возврата не должен протечь в путь обычных алертов. Сам `do_alert` в reconciler не трогается и снаружи не дергается - публичного CLI-входа у него нет, гонять его через чтение реализации смысла нет.
- R12 (регресс §1): ни `claude-agent-ask`, ни прогон, ни хук подтверждений (`claude-agent-permit`, контракт V2.4 - читать разрешено) не зовут alert-команду с question-detail (барьер второго producer'а, продолжение V2.5 T15).
- R13: агент без открытых вопросов -> подкоманда ничего не печатает и ничего не пишет.

## 9. Критерии приемки

- Вопрос, заданный агентом, приезжает карточкой в пределах минуты, без участия прогона (R1, R12).
- Без ответа напоминания идут лесенкой и не учащаются (R3); недоставленная карточка повторяется, а не теряется (R4).
- Ответ, снуз и закрытие вопроса гасят напоминания (R5, R6, R7).
- Обычные алерты и их 6-часовой дедуп не изменились (R11).
