# V2.0: runtime drain-and-exit для event-агентов

Контракт этапа (SDD): публичные интерфейсы и инварианты. Реализация обязана пройти тесты, выведенные из этого документа, не наоборот.

## Цель

Event-агент типа "задача" не должен держать вечный процесс и RAM-слот admission, когда ему нечего делать. Вводится второй рантайм: юнит поднимается только при готовых конвертах, обрабатывает их и завершается сам. Существующие event-агенты (`loop`) не меняются ни в чем.

## 1. Поле спеки

```yaml
# spec.yaml
runtime: drain        # loop | drain; отсутствие поля = loop
```

- Читается через `spec_get(dir, ".runtime")`: пустая строка -> `loop`.
- Любое значение кроме `loop`/`drain`/пустого - ошибка валидации агента (fail-closed: юнит не стартует, attention `control_invalid` по существующему пути валидации спеки).
- Поле применимо только к `type: event`; для `type: mission` игнорируется.

## 2. `claude-agent-run drain <agent-dir>`

Новая подкоманда. Семантика - цикл существующей итерации executor'а (`executor_cycle`) до первого не-`ran` исхода:

1. Взять `.executor.lock` (без ожидания; занят -> exit 5, как `loop`/`step`).
2. Повторять `executor_cycle` пока исход `ran`.
3. На первом исходе из {`idle`, `exhausted`, `infra_wait`}: финальный state_write с `phase="sleeping"` и `status_line="drained:<исход>"` (имя поля в state-файле - `status_line`), напечатать исход в stdout, **exit 0**.

Инварианты:

- Никакого `sleep(CYCLE_S)`-ожидания: не-`ran` исход означает немедленный выход.
- `recovery_pass`, budget-гейт, infra-гейт, дедуп, ретраи - ровно те же, что в `loop` (общий `executor_cycle`, не копия логики).
- Kill-safety как у `loop`: обработчиков сигналов не добавляем; durable-порядок записей внутри `executor_cycle` не меняется; flock снимается ядром.
- `intake` изнутри не зовется (остается хостом в reconciler, как сегодня).

## 3. `inbox-status`: поле `ready`

К существующему JSON добавляется:

```json
"ready": <int>   // pending-конверты, готовые к запуску СЕЙЧАС:
                 // не quarantined и (next_attempt_at отсутствует или <= now)
```

Условие обязано совпадать с условием выбора в `pick_ready` (единый предикат в коде, не копия). Остальные поля не меняются.

## 4. Reconciler: гейт подъема для `runtime: drain`

Точки изменения - три, все существующие пути сохраняются:

1. **exec_cmd**: для event-агента с `runtime: drain` юнит запускается как `claude-agent-run drain "$dir"` вместо `loop`. Все прочее в `systemd-run` (юнит-имя, env, MemoryMax, KillMode) - без изменений.
2. **Ready-гейт в ветке старта** (класс `ABSENT`, ветка `WANT_START`): для `runtime: drain` заявка на старт подается только если:
   - `ready > 0` (из `inbox-status`, уже вызываемого в `event_maintenance` - без дополнительного subprocess), И
   - `runner-status.retry_at` отсутствует или `<= now` (не будить юнит в окно infra-бэкоффа - иначе churn "поднялся-вышел" каждые 2 прохода при лежащем API).
   При `ready == 0`: тихий выход из обработки агента - без attention, без hold, без событий. Это штатное "задаче нечего делать".
3. **Выход юнита - штатный**: изменений НЕ требуется - подтверждено разведкой: смерть юнита дает `ORPHANED_LEASE` -> `shutdown_agent` -> lease освобождается при доказанно пустом cgroup, без attention и без `resume_fails`. Контракт фиксирует это как инвариант: drain-выход не должен порождать attention/resume_fails ни на каком пути.

Admission (RAM-бюджет, один старт за проход) - без изменений: drain-агент учитывается в бюджете только пока юнит жив.

## 5. Что явно НЕ меняется (регресс-инварианты)

- Спека без `runtime` -> поведение `loop` байт-в-байт: тот же exec_cmd, тот же безусловный старт при desired=running, та же обработка выхода.
- `step`, `spool-put`, `intake`, DLQ, recovery, бюджеты - интерфейсы и семантика не меняются.
- mission-агенты не затрагиваются вовсе.
- `EVENT_ALLOWED_ATT` не расширяется.

## 6. Тесты (выводятся из контракта; стиль - существующий bash-фреймворк tests/)

Юнит-уровень (`tests/test-agent-run.sh`, mock-claude через `CLAUDE_BIN`):

- T1 `drain` на пустом inbox: exit 0, stdout `idle`-исход, state `sleeping/drained`.
- T2 `drain` с N=3 ready-конвертами: обработаны все 3 (done), exit 0 после последнего.
- T3 `drain` при исчерпанном бюджете: exit 0, исход `exhausted`, конверты не тронуты.
- T4 `drain` при infra-фейле: exit 0, исход `infra_wait`, конверт остается pending.
- T5 второй `drain` при занятом `.executor.lock`: exit 5.
- T6 `drain` с конвертом `next_attempt_at` в будущем: не берет, выходит `idle`.
- T7 `inbox-status.ready`: pending=3, из них 1 quarantined и 1 с будущим `next_attempt_at` -> `ready == 1`.
- T8 регресс: `step`/`loop`-путь (существующие кейсы) зелены без правок самих тестов.

Интеграционный (fault-suite, реальный systemd, сценарий S20):

- S20a: drain-агент, desired=running, spool пуст -> юнит НЕ стартует ни на одном проходе; событие в spool -> intake -> юнит стартовал, обработал, вышел; lease освобожден; attention пуст; `resume_fails` не вырос.
- S20b: второе событие после засыпания -> цикл повторился (generation вырос).
- S20c: соседний loop-агент в том же прогоне ведет себя как в S16 (регресс).

## 7. Критерии приемки этапа (из плана v2)

- Задача без событий = ноль процессов (S20a до события).
- Событие -> поднялся, обработал, лег (S20a/b).
- Спека без `runtime` -> loop байт-в-байт (T8, S20c).
