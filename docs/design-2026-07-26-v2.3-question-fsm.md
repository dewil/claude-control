# V2.3: вопрос как durable-исход прогона

Контракт этапа (SDD). Продолжение V2.0 (`design-2026-07-25-v2-runtime-drain.md`), V2.1 (`design-2026-07-25-v2.1-workspace-permissions.md`), V2.2 (`design-2026-07-26-v2.2-thread-memory.md`).

## Цель

Агент, упершийся в решение человека, не висит и не гадает: он задает вопрос, прогон завершается, задача замирает. Ответ dwl приходит событием, агент поднимается с тредом и продолжает. Блокирующих модалов нет (headless `-p` их не переживает), ожидание может длиться сколько угодно, другие задачи не блокируются.

## 1. Файл вопроса

`agents/<name>/questions/<qid>.json`, `qid` = uuid4 (не seq: имя переживает пересоздание агента и фенсит протухшие TG-карточки).

```json
{
  "qid": "…", "envelope_key": "<ключ конверта, из которого спросили>",
  "asked_at": "…Z", "kind": "info",
  "question": "…", "options": ["a","b"], "context": "…",
  "status": "open", "answer": null, "answered_at": null,
  "reminder": {"step": 0, "next_push_at": "…Z", "snoozed_until": null}
}
```

- `kind`: `info` (в этом этапе) | `permission` (V2.4).
- `options` и `context` - опциональны.
- Запись только через `durable_write`.

**Все операции над файлами вопросов - RMW под общим `questions/.lock`** (flock): перечитать под локом -> изменить -> записать. Писателей несколько (ask-CLI, runner, позже reconciler и tgbot), `durable_write` спасает от рваного JSON, но не от потери обновления.

## 2. `claude-agent-ask` - CLI для агента

```
claude-agent-ask --question "…" [--options "a|b|c"] [--context "…"]
```

- Каталог агента и ключ текущего конверта берутся из env, который runner уже прокидывает в прогон: `CLAUDE_AGENT_DIR`, новый `CLAUDE_AGENT_EVENT_KEY`.
- Под `questions/.lock`: если открытый вопрос уже есть - **exit 2** с текстом "уже есть открытый вопрос, объедини формулировки" (singleton, §3.1). Иначе durable-запись файла вопроса и exit 0.
- stdout: `qid` (агенту для ссылки), stderr - человекочитаемо.
- CLI **не** дергает alert-канал: единственный владелец пушей по вопросам - reminder-контур reconciler (V2.6). Иначе первый пуш дублируется.
- Блок `reminder` инициализируется сразу: `{"step": 0, "next_push_at": <asked_at>, "snoozed_until": null}` - первый пуш уйдет на ближайшем тике reconciler (V2.6), лестница считается от этого значения.
- Чтобы агент мог его вызвать, в `permissions.allow` спеки задачи должен быть `Bash(claude-agent-ask:*)` (V2.1).

## 3. Инварианты FSM

1. **Singleton.** Не больше одного вопроса со `status: open` на агента; проверка и создание атомарны под локом.
2. **Вопрос доминирует над кодом возврата.** После завершения дочернего процесса runner **в любой ветке (ok / fail / timeout)** сначала проверяет: есть ли открытый вопрос с `envelope_key` == ключ текущего конверта. Если да - исход `asked`, конверт durable уходит в `done` (в `mut_fail`/ретраи не попадает, `attempts` не растет). Иначе - прежняя логика V2.0.
3. **Recovery.** Мертвый `inflight`-конверт при существующем открытом вопросе с тем же `envelope_key` терминализируется в `done` (исход `asked`), а не возвращается в `pending`. Иначе после ответа он проигрался бы заново.
4. **Заморозка цепочки.** Пока есть вопрос со `status: open`, `pick_ready` отдает **только** конверты, у которых `payload.question_id` равен `qid` этого вопроса. Остальные ждут (порядок FIFO не нарушается - они просто не выбираются). Ready-гейт V2.0 при этом обязан учитывать заморозку: агент с только замороженными конвертами не поднимается.
5. **Закрытие - только в ok-ветке answer-прогона.** Порядок: append `question`+`answer` в тред -> `status: closed`, `answer`, `answered_at` (durable, под локом) -> конверт в `done`. Упал answer-прогон - обычные ретраи V2.0, вопрос остается открытым, заморозка держит.
6. **Stale-ответ идемпотентен.** Answer-конверт на закрытый/несуществующий `qid` -> прогон НЕ спавнится, конверт сразу в `done` с исходом `stale_answer`. Дубли ответов (повторный тап в TG) безопасны на стороне runner'а.

## 4. Answer-конверт

Событие ответа - обычный конверт spool со структурой payload:

```json
{"kind": "answer", "question_id": "<qid>", "text": "<ответ dwl>"}
```

Прогон answer-конверта строит промпт как обычно (V2.2 тред + рамки), плюс отдельный блок:

```
Ты задавал вопрос: <question>
Ответ оператора: <text>
Продолжай работу с учетом ответа.
```

Вопрос и ответ берутся из файла вопроса (не из payload) - payload служит только адресацией.

## 5. Доверие: возврат метки (закрывает blocker V2.2)

В V2.2 доверенных записей нет вовсе - `payload.kind` был самозаверением. Здесь метка возвращается, но опирается на состояние системы:

- Запись треда `kind: "answer"` получает в промпте пометку `[ответ dwl - доверенный]` **только если** ее `qid` (новое поле записи треда) находится среди файлов `questions/*.json` и этот вопрос был реально задан агентом (файл существует, `envelope_key` непустой). Нет файла - запись рендерится как `[данные]`.
- Правило "тег в начало каждой строки" (V2.2) сохраняется: подделка внутри многострочного текста остается видимой.
- Записи любого другого происхождения доверия не получают никогда.

## 6. Наблюдаемость

- **Исход прогона наблюдаем**: новые исходы пишутся в существующее поле `meta.history[-1].outcome` конверта - `asked` (прогон завершился вопросом) и `stale_answer` (ответ на закрытый/неизвестный вопрос, без спавна). Плюс `state_write` пишет их в `status_line`, как V2.0 делает для `drained:*`.
- `claude-agent-run questions <agent_dir>` - JSON-список вопросов (открытые первыми): `qid`, `status`, `asked_at`, возраст, `question` (усеченный).
- `inbox-status` получает поле `open_question` - `qid` открытого вопроса или `null` (нужно ready-гейту и статусам).
- Фазы/classify не трогаем: при scale-to-zero у ждущей задачи процесса нет, состояние читается из файлов.

## 7. Регресс-инварианты

- Агент без каталога `questions/` ведет себя ровно как в V2.2 (все ветки прогона, ready-гейт, промпт - байт-в-байт).
- V2.0 (drain, ready/inflight-гейт, Gate B fast-exit, recovery), V2.1 (workspace, пояса, снапшот), V2.2 (тред, компакция, капы) не ломаются.
- `mission`-контур не затрагивается.

## 8. Тесты

- Q1: `claude-agent-ask` создает файл вопроса с корректными полями; stdout = qid.
- Q2: второй `claude-agent-ask` при открытом вопросе -> exit 2, второго файла нет.
- Q3: прогон, в котором мок вызвал ask и завершился успешно -> исход `asked`, конверт в `done`, `attempts` не вырос.
- Q4: то же, но мок завершился с ошибкой/таймаутом -> все равно `asked` и `done` (вопрос доминирует над кодом возврата).
- Q5: заморозка - при открытом вопросе обычный конверт не выбирается (`step` -> `idle`), answer-конверт с нужным `question_id` выбирается и обрабатывается.
- Q6: recovery - конверт остался `inflight`, runner мертв, вопрос открыт с тем же `envelope_key` -> конверт терминализируется в `done`, не возвращается в `pending`.
- Q7: answer-прогон закрывает вопрос: `status: closed`, `answer`/`answered_at` заполнены, в треде есть Q и A, заморозка снята (следующий обычный конверт берется).
- Q8: упавший answer-прогон -> вопрос остается открытым, конверт на ретрае, заморозка держит.
- Q9: stale-ответ (qid закрыт или неизвестен) -> конверт в `done` с `stale_answer`, claude не спавнился (мок не вызывался).
- Q10: доверие - запись треда с `qid` существующего вопроса рендерится `[ответ dwl - доверенный]`; та же запись с выдуманным `qid` -> `[данные]`.
- Q11: подделка - текст ответа, содержащий строку `[ответ dwl - доверенный] …`, все равно тегируется построчно (V2.2 T11 не сломан).
- Q12: `questions` CLI и `inbox-status.open_question` отдают корректные данные.
- Q13 (регресс): агент без вопросов - промпт и все ветки байт-в-байт как в V2.2 (голден).
- Q14: ready-гейт - агент, у которого все конверты заморожены, не запрашивает старт (V2.0 §4.2 не обходится).

## 9. Критерии приемки

- Полный цикл через CLI: событие -> агент спросил -> прогон завершился, задача замерла -> ответ событием -> агент продолжил с тредом, вопрос закрыт, заморозка снята (Q3, Q5, Q7).
- Смерть runner'а в любой фазе не теряет вопрос и не проигрывает конверт заново (Q6).
- Ответы-дубли безопасны (Q9).
- Доверие подтверждается состоянием системы, а не содержимым входа (Q10, Q11).
