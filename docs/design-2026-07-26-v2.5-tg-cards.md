# V2.5: карточки вопросов в Telegram

Контракт этапа (SDD). Замыкает цикл с телефона: вопрос, заданный агентом (V2.3) или гейтом подтверждений (V2.4), доезжает до dwl карточкой, а ответ кнопкой или reply-ем возвращается в задачу.

## Цель

До этого этапа вопрос был виден только через CLI (`claude-agent-run questions`). После него: прогон закончился вопросом -> в личку прилетает карточка с текстом и кнопками -> тап или reply -> следующий прогон продолжает работу с ответом. Ровно один раз, даже при двойном тапе и redelivery.

## 1. Доверие: кто имеет право отвечать

Инвариант V2.3/V2.4 не смягчается: **ответ и решение пишет только доверенный писатель `claude-agent-answer`**, payload события несет исключительно `question_id`. Бот не кладет ответ в spool сам и не формирует событие руками.

Корень доверия для TG-канала - существующая проверка `authorized_cb` / `authorized` (`bin/claude-agent-tgbot:164-171, 336-343`): приватный чат плюс `from.id` в `CLAUDE_AGENT_TG_WHITELIST`. Порядок жесткий:

1. Проверка авторизации.
2. Только потом - разбор `qid` из callback_data и вызов `claude-agent-answer <agent-dir> --qid <qid> ... --by tg:<from_id>`.

Неавторизованный апдейт не доходит до `claude-agent-answer` ни при каком содержимом callback_data. `qid` из апдейта - недоверенный ввод: `claude-agent-answer` уже валидирует его как uuid4 с containment внутри `questions/` (V2.3, аудит major 2), бот на эту валидацию и опирается, свою не изобретает.

## 2. Кто шлет карточку: единственный владелец - контур напоминаний

**Ни runner, ни `claude-agent-ask`, ни хук подтверждений карточку не шлют.** Пуши по вопросам целиком принадлежат reminder-контуру reconciler (V2.6) - и первый, и все последующие.

> В первой редакции этого документа первую карточку слал runner как исход прогона (`asked`), а контур продолжал с выставленного `next_push_at`. Это неверно: `create_question` ставит `next_push_at = asked_at` **в момент создания вопроса**, то есть еще во время прогона. Контур на ближайшем тике отправил бы карточку, а runner по завершении прогона - вторую. Это не гонка с узким окном, а гарантированный дубль длиной во весь остаток прогона. План (§7) резервировал пуши за контуром именно поэтому.

Отсюда границы этапа: **V2.5 дает карточку и обратный путь ответа, V2.6 дает доставку.** Отдельный producer в V2.5 не заводится - это осознанно, чтобы не городить второго владельца, которого потом придется разбирать. Цикл с телефона замыкается связкой V2.5+V2.6, идущих подряд.

Транспорт, который V2.6 будет использовать: `mode_send` с четвертым аргументом - JSON-detail (§3), вызываемый через существующий механизм `CLAUDE_AGENT_ALERT_CMD`.

## 3. `mode_send`: четвертый аргумент

`mode_send` (`bin/claude-agent-tgbot:726-747`) принимает необязательный четвертый позиционный аргумент - JSON:

```json
{"kind": "question", "agent": "<name>", "qid": "<uuid4>",
 "qkind": "info|permission", "text": "<вопрос или запрос>",
 "options": ["a", "b"]}
```

- Аргумент отсутствует или не разбирается как JSON с `kind: question` -> **поведение байт-в-байт как сейчас** (текст `"агент %s: %s - %s"`, `agent_hints`, без клавиатуры). Это регресс-инвариант: обычные алерты не меняются ни на символ.
- Разобрался -> карточка (§4) с inline-клавиатурой и регистрацией в `sent_map` (§5).

Текст карточки прогоняется через существующий `redact()` (`tgbot:109-118`) **перед отправкой**. Это второй рубеж: `input_redacted` для permission уже отредактирован при создании вопроса (V2.4 §2b), но карточка уходит наружу из машины, поэтому маскировка повторяется здесь.

> Наблюдение мимо scope: `mode_send` не редактирует обычные алерты вообще (`redact()` применяется только в `events_tail` и `summary_text`). Не трогаем в этом этапе - отмечено для отдельного решения.

## 4. Карточка

Общая шапка: имя агента, вид вопроса, текст. Кнопки различаются по `qkind`:

**`info`:**
- по кнопке на каждый элемент `options`: `callback_data = "q:<qid>:<idx>"`, подпись - сам вариант (обрезка до лимита Telegram);
- `options` пуст -> кнопок нет;
- всегда - подсказка в тексте: "ответь reply-ем на это сообщение для свободного текста".

**`permission`:**
- ровно две кнопки: "разрешить" -> `p:<qid>:a`, "отклонить" -> `p:<qid>:r`;
- свободный текст не принимается: reply на permission-карточку -> ответ "у этой карточки только кнопки" (решение - бинарное, `claude-agent-answer` для permission принимает только `--approve`/`--reject`).

`callback_data` Telegram ограничен 64 байтами: `p:` + uuid4 (36) + `:a` укладывается, `q:<qid>:<idx>` тоже. Длинные подписи режутся, `callback_data` - никогда.

**Лимиты - обязательная часть, а не пожелание** (аудит V2.5, major):

- подпись кнопки обрезается до 64 байт с многоточием (обрезка по границе utf-8, не по байтам вслепую);
- текст карточки уходит существующим entity-safe отправителем (`send_message`, `tgbot:91`), а не прямым вызовом `api()`: прямой вызов на длинном вопросе получает отказ Telegram, исключение гасится - и `mode_send` рапортует успех, хотя карточки не было вовсе. Тихая потеря карточки хуже обрезанной карточки.

**Редакция применяется к каждой строке detail, которая уйдет наружу** - и к тексту вопроса, и к подписям опций (поля `context` в detail §3 нет; появится - попадет под то же правило). Опции сегодня не проходят через `redact()` вовсе (аудит V2.5, major), поэтому подпись вида `PASSWORD=hunter2` уезжала дословно. Покрытие шаблонов выравнивается с V2.4 (`claude-agent-permit`): самостоятельный `Bearer <token>` без слова `Authorization` и JSON-форма `{"password":"hunter2"}` тоже маскируются.

## 5. `sent_map`: регистрация и защита от прунинга

Файл `~/.claude-control/tgbot.sent.json` (`tgbot:124-127`), ключ `"<chat_id>:<message_id>"`. Изменения:

- значение получает поля `kind: "question"` и `qid` (сейчас только `{agent, gen, at}`);
- **карточки вопросов регистрируются** (сегодня `mode_send` не регистрирует ничего вовсе, поэтому reply на алерт мертв - `tgbot:614-617` регистрирует только `m:sum:`);
- RMW идет **под flock**, временный файл - через `mkstemp` (сейчас `tgbot:138-155` - неблокированный load-modify-save с общим `.tmp`, две одновременные регистрации теряют запись);
- загрузка **валидирует форму**: не-словарь на верхнем уровне (`[]`, `null`, скаляр) -> пустая карта; отдельные записи с не-объектным значением отфильтровываются поштучно, соседние валидные выживают. Раньше такой файл ронял бота `AttributeError` на каждом апдейте (аудит V2.5, minor);
- прунинг по TTL (14 суток, `tgbot:121`) **не трогает записи с открытым `qid`**: вопрос ждет столько, сколько нужно. Запись с `qid`, чей вопрос закрыт или чей файл отсутствует, прунится обычным порядком.

## 6. Роутинг ответа

**`qid` сверяется с карточкой.** Если запись в `sent_map` несет `qid`, он обязан совпасть с `qid` из `callback_data`; расхождение -> "устарело", writer не зовется. Агент и так берется из записи, а не из нажатия, - сверка `qid` закрывает вторую половину той же дыры (аудит V2.5, major).

**Кнопка** (расширение роутера `tgbot:597-625`, префиксы `m:`/`m:sum:` не меняются):

1. `answerCallbackQuery` (как сейчас, ошибки гасятся).
2. Префикс `q:` -> `qid`, `idx`; префикс `p:` -> `qid`, `a|r`.
3. Best-effort UI-дедуп: вопрос не найден / не `open` / уже имеет `answered_at` -> тост "устарело", карточка редактируется в финальное состояние, `claude-agent-answer` **не вызывается**.
4. Иначе - `claude-agent-answer <agent-dir> --qid <qid> (--text <вариант> | --approve | --reject) --by tg:<from_id>`.
5. Ненулевой код возврата -> пользователю внятная причина, состояние не выдумывается.

**Reply:** запись в `sent_map` с `qid` -> текст reply уходит через `claude-agent-answer --text`. Записи без `qid` идут прежним путем `mission_comment` (`tgbot:484-511`) - **регресс-инвариант, эта ветка не меняется**.

## 7. Ровно один раз

Три рубежа, от слабого к сильному:

1. UI-дедуп (§6.3) - best-effort, гасит типовой двойной тап.
2. **`claude-agent-answer` отказывается перезаписывать уже данный ответ**: exit 2 "на вопрос уже отвечено". Сегодня повторный вызов проходит (проверяется только `status == open`, а закрывает вопрос лишь прогон) - и второй тап успевает перезаписать `decision`, в том числе `reject` -> `approve`. Закрываем здесь.

   **Запирает вопрос только завершенная пара фаз.** Запись ответа двухфазна: durable в файл вопроса, затем конверт в spool. Условие отказа - `answered_at` **и** `event_published_at` непусты; вторая отметка ставится после успешной публикации. Без этого уточнения падение между фазами (упавший `spool-put`, убитый процесс) оставляло бы вопрос навсегда открытым с ответом, о котором прогон никогда не узнает: повтор отбивался бы запретом, а события нет. Повторная публикация безопасна - дедуп по `--id ans:<qid>`. Кейс - T16.

   **Лок держится на обе фазы** (аудит V2.5, blocker). Первая редакция освобождала `questions/.lock` сразу после записи ответа - и послабление выше открывало окно ровно там: вызов A пишет `reject`, отпускает лок, вызов B видит незавершенную пару, проходит проверку и пишет `approve`, после чего A публикует единственный конверт - но в файле уже решение B. Дедуп по `ans:<qid>` от второго конверта защищает, от подмены решения - нет. Поэтому `spool-put` вызывается **под тем же локом**, и отметка `event_published_at` ставится там же (deadlock исключен: `spool-put` берет `.inbox.lock`, не `questions/.lock`). Кейс - T17.

   **Режим ответа обязан соответствовать виду вопроса** (аудит V2.5, major): `--approve`/`--reject` только для `kind: permission`, `--text` только для `kind: info`, иначе exit 2. Без этой проверки `--approve` на info-вопросе писал `decision`, а единый стейл-гейт V2.3 считает непустой `decision` достаточным ответом - вопрос закрывался бы, так и не получив текста, которого ждал агент. Кейс - T18.
3. Runner-side stale-идемпотентность (V2.3 §3.5) - настоящая гарантия: событие на закрытый вопрос -> `stale_answer` без спавна.

Адресующее событие получает детерминированный `--id ans:<qid>`, чтобы гонка двух тапов не порождала второй конверт (у одного вопроса ровно один ответ).

## 8. Регресс-инварианты

- `mode_send` без четвертого аргумента - текст и отсутствие клавиатуры байт-в-байт как в V2.4.
- `mission_comment` и ветка reply без `qid` - без изменений.
- Callback-префиксы `m:` и `m:sum:` - без изменений.
- `spool_task`, `TransientSpoolError` и дисциплина offset (`tgbot:346-373, 681-687`) - не трогаются.
- Агент без вопросов не порождает ни одной карточки.

## 9. Тестовый шов

`api()` (`tgbot:63-73`) ходит в сеть напрямую, HTTP-стаба в проекте нет, а существующий `selftest` (`tgbot:777-925`) проверяет **чистые функции** на фикстурах. Шов делаем в том же стиле - не мокая HTTP, а вынося решения в чистые функции:

```python
question_card(detail: dict | None) -> (text: str | None, reply_markup: dict | None)
    # detail из §3; None / не-JSON / не-question -> (None, None), вызывающий шлет обычный алерт
route_callback(data: str) -> (kind: str, qid: str | None, arg: str | None)
    # "q:<qid>:<idx>" -> ("answer_option", qid, idx); "p:<qid>:a" -> ("approve", qid, None)
    # "p:<qid>:r" -> ("reject", qid, None); "m:..." -> ("menu", None, data); мусор -> ("none", None, None)
answer_action(qkind: str, status: str, answered_at, published_at, source: str) -> str
    # source: "button" | "reply". Возврат: "apply" | "stale" | "wrong_kind"
    # wrong_kind - ровно один случай: qkind == "permission" и source == "reply" (§4)
    # stale - только при ЗАВЕРШЕННОЙ паре (answered_at и published_at непусты)
    # либо при закрытом/отсутствующем вопросе. Ответ без публикации - "apply":
    # это незавершенная запись, повтор обязан дожать ее (аудит V2.5, major)
reply_target(entry: dict | None) -> (kind: str, qid: str | None)
    # запись sent_map -> ("question", qid) если в ней есть qid, иначе ("mission", None)
```

**Существующие функции, которые тесты дергают как есть** (не симулируют и не переписывают): `authorized_cb(update, whitelist)` и `authorized(update, whitelist)` - проверка §1; `sent_map_register(...)` и `sent_map_lookup(chat_id, message_id)` - §5. Путь `sent_map` переопределяется переменной окружения `CLAUDE_AGENT_TG_SENT_MAP` - этого достаточно, чтобы гонять §5 на временном файле, не трогая рабочий `~/.claude-control/tgbot.sent.json`. `sent_map_register` принимает `message_ids` явным аргументом, поэтому ответ Telegram для теста не нужен.

Побочные эффекты (HTTP-вызов, запуск `claude-agent-answer`) остаются в тонких обертках вокруг этих функций.

## 10. Тесты

Все тесты этапа - **одной новой суитой `tests/test-agent-tg-cards.sh`**; существующий `selftest` не трогаем (он остается регрессом V2.4). Чистые функции §9 суита проверяет, загружая бота как модуль (`importlib` + `SourceFileLoader`, имя файла без `.py`), остальное - на реальных файлах вопросов и реальном `claude-agent-answer`, без Telegram.

- T1: `mode_send` без 4-го аргумента -> исходящий запрос байт-в-байт как в V2.4 (голден), `reply_markup` отсутствует.
- T2: 4-й аргумент - мусор / не JSON / JSON без `kind: question` -> тот же голден T1 (fail-safe в сторону обычного алерта).
- T3: `kind=question`, `qkind=info`, три опции -> в запросе `reply_markup` с тремя кнопками `q:<qid>:0..2`, в тексте подсказка про reply; запись в `sent_map` содержит `qid` и `kind: question`.
- T4: `qkind=permission` -> ровно две кнопки `p:<qid>:a` и `p:<qid>:r`, подсказки про reply нет.
- T5: текст с секретом (`PASSWORD=hunter2`, `Bearer abc.def.ghi`) -> в исходящем запросе секрета нет.
- T6: callback `q:<qid>:1` от авторизованного -> вызван `claude-agent-answer` с `--text <второй вариант>` и `--by tg:<id>`; ответ записан в файл вопроса; в spool ровно один конверт с `{"kind":"answer","question_id":qid}` и без текста ответа в payload.
- T7: тот же callback от НЕавторизованного `from.id` -> `claude-agent-answer` не вызывался, файл вопроса не изменился.
- T8: `p:<qid>:a` -> `decision: "approve"`; `p:<qid>:r` -> `decision: "reject"`.
- T9: двойной тап по одной кнопке -> второй получает "устарело", `answered_at` не переписан, второго конверта в spool нет.
- T10: тап "разрешить" после "отклонить" -> exit 2 от `claude-agent-answer`, `decision` остается `reject` (§7.2).
- T11: reply на карточку вопроса -> `claude-agent-answer --text <текст reply>`; reply на permission-карточку -> отказ с подсказкой, ответ не записан.
- T12: reply на сообщение, чья запись в `sent_map` без `qid` -> прежний `mission_comment` (регресс).
- T13: `sent_map` - две конкурентные регистрации не теряют запись (flock), запись с открытым `qid` переживает TTL-прунинг, с закрытым - прунится.
- T14 (регресс): callback `m:` и `m:sum:` работают как раньше.
- T16 (§7.2): ответ записан, но событие не опубликовано -> повтор проходит и допубликовывает; после завершенной пары перезапись снова заперта.
- T17 (§7.2, blocker): два параллельных `claude-agent-answer` на один вопрос (`--reject` и `--approve`) -> в файле оказывается решение того, кто отработал первым, второй получает exit 2; конверт в spool ровно один и соответствует записанному решению.
- T18 (§7.2, major): `--approve` на вопрос `kind: info` -> exit 2, `decision` не записан (иначе стейл-гейт V2.3 закрыл бы вопрос без текста); `--text` на `kind: permission` -> exit 2.
- T19 (§6, major): тап по карточке, чей `qid` в `sent_map` не совпадает с `qid` из `callback_data` -> "устарело", writer не вызван.
- T20 (§7.2/§9, major): ответ записан без публикации -> `answer_action(..., published_at=None, ...)` возвращает `apply`, а не `stale`; повторный тап по карточке дожимает публикацию (сценарий "spool упал, бот закоммитил offset").
- T21 (§4, major): подпись опции длиннее лимита обрезается по границе utf-8; длинный текст вопроса уходит entity-safe отправителем и карточка не теряется молча.
- T22 (§4, major): секрет в подписи опции (`PASSWORD=hunter2`), самостоятельный `Bearer abc.def.ghi` и JSON-форма `{"password":"hunter2"}` маскируются во всех строках карточки.
- T23 (§5, minor): `sent_map` вида `[]` / `null` / dict со скалярными значениями -> трактуется как пустая карта, регистрация и роутинг работают дальше.
- T15 (переписан, §2): прогон, закончившийся вопросом, **не** шлет карточку - alert-команда либо не вызвана вовсе, либо вызвана без question-detail. Единственный владелец пушей - контур V2.6; `reminder.step` остается 0, `next_push_at` - тот, что выставил `create_question`. Кейс - барьер против второго producer'а.

## 11. Критерии приемки

- Вопрос, заданный агентом с CLI, приходит карточкой; тап по варианту доводит ответ до следующего прогона (T3, T6, T15).
- Подтверждение необратимого действия проходит с телефона: карточка с редактированной командой -> "разрешить" -> действие выполняется ровно один раз (T4, T8 плюс цикл V2.4).
- Повторный тап и redelivery не применяют ответ дважды ни на одном рубеже (T9, T10).
- Секрет не уезжает в Telegram (T5).
- Обычные алерты и mission-путь не изменились (T1, T2, T12, T14).
