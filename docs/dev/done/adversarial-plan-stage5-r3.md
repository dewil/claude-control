Та же сессия. В r1/r2 ты вскрыл фундаментальный предел transcript-transfer
(единственный писатель между машинами кооперативными ФС не гарантируется). Решение

## Что теперь (прочитай `docs/design-2026-07-13-stage5-takeover.md` v3 целиком)

Кросс-машинный handoff = обычный fresh mission-агент на VM от точного запушенного
commit, mission.md = бриф. Транспорт кода - git push/fetch, не scp транскрипта.
Удалены: release-маркер, fence-by-MOVE, sid-registry, consumed-ledger,
transcript-move, push-ветка в reconciler, вся crash-матрица v2. Ново только:
(1) тонкий stateless Mac-хелпер (git push + бриф + ssh create); (2) VM create
`--base-commit <sha>` (fetch + `cat-file -e` + `worktree add ... <sha>`).

## Задача раунда 3 (тугая рамка)

Реши ГЛАВНОЕ: снимает ли отказ от разделяемого session_id весь класс двойного
владения из r1/r2? Осталась ли хоть одна нить, где Mac-сессия и VM-агент делят
изменяемое состояние так, что расходятся/конфликтуют (в модели "ошибки, не
злоумышленник")?

Прицельно проверь:
1. **Двойное владение**: два session_id, две независимые сессии, общий только
   git-remote. Есть ли ещё что-то общее и изменяемое (реестр? worktree? relay-имя?
   namespace-slug? файл сессии по случайному совпадению sid)?
2. **`--base-commit`**: `fetch` + `cat-file -e` + `worktree add <sha>` - дыра, где
   worktree окажется в мусорном/пол-состоянии (commit есть как объект, но дерево
   не выписывается; detached vs -b ветка; commit есть, но submodule/LFS не
   подтянут; force-push между fetch и add)? fail-closed при отсутствии commit -
   реально до side-effect'ов (worktree add не частично)?
3. **Потеря транскрипта**: что-то КРИТИЧЕСКОЕ (не память-удобство) теряется, из-за
   чего fresh-агент не сможет продолжить корректно (напр. состояние вне git -
   uncommitted, но нужное)? Дизайн требует clean-tree на Mac - этого достаточно,
   или есть нужное состояние вне git И вне брифа?
4. **Тонкий stateless хелпер**: отсутствие durable-FSM - реально ок (нечего
   восстанавливать), или есть шаг, где крах оставляет вредный побочный эффект
   (напр. push случился, create нет - вредно? create случился, а спек/mission не
   долетели - агент на VM без миссии)?
5. **Регресс существующего create**: `--base-commit` опционален; ломает ли он
   текущий fresh-путь (без флага) или атомарность create этапа 2?

НЕ репортить: стиль; отложенную автогенерацию брифа (v2, UX); отсутствие переноса
памяти (это принятое решение, не дефект).
