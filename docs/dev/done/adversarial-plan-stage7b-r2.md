## Что изменено против раунда 1

`docs/design-2026-07-13-stage7b-harvester.md` - прочитай целиком (v2).
Сводка правок по твоим находкам раунда 1:

1. Д0 overclaim durability -> убран; note в detail той же control-cas
   транзакции (атомарно, не отдельный append); events.jsonl объявлен
   best-effort, harvester терпит потерю.
2. Секреты в вечном логе -> переосмыслен threat-model (Д5): локальный
   events.jsonl = операторский текст (класс commit-месседжа, не экспорт);
   маскировка на границе ЭКСПОРТА (ledger/digest/upstream); источник (b)
   вырезан -> нет вектора "агент surface'нул секрет".
3. Источник (b) транскрипт -> ВЫРЕЗАН из v1 (Д6). v1 = только (a).
4. correction-id -> incarnation-safe: `sha1(role|project|agent|event_at|
   event_seq|sha1(note))` (Д4).
5. Гонки collect/propose -> per-key fcntl-flock + терпимость рваного
   хвоста (Д10).
6. Семантика (a) -> фильтр `actor=operator`, revise отдельно от reject,
   accept-ноты выброшены (Д3).
7. candidate-pass -> зафиксирован контракт приёмщика §8.7 (бан тулов,
   пустой cwd, капы, timeout, no-clobber, fencing) + детерминированная
   валидация вывода: correction_ids ⊆ входа, уникальны, >=MIN, не покрыты,
   иначе кластер отброшен (Д7).
8. emitted.jsonl -> схема + candidate_id=sha1(sorted ids) + lifecycle
   proposed/pending-upstream/rejected БЕЗ преждевременного applied; rejected
   не хоронит поправки, отклонённые essence показываются LLM (Д8).
9. Ключ -> (проект, роль); spec.role валидируется при create; slug в пути
   (Д2).
10. Граница role/ -> механическая: LLM без write-тулов, детерминированный
    код с фиксированным allowlist корней, кода записи в role/ нет (Д11).
11. approve -> полный upstream-бриф + RMW canon.yaml + pending-upstream
    (не applied) (Д9).
12. Критерий -> разделён на verifiable-delivery (билд) и outcome-метрику
    (эксплуатация).

## Проверь (ломай заново)

- Атомарность Д0: note в `--detail` control-cas - точно ли append_event
  идёт под тем же flock/seq, что set (посмотри cmd_control_cas в
  `bin/claude-agent-io`)? Если append_event ВНЕ транзакции - Д0 не закрыт.
- Маскировка Д5: новый threat-model честен, или есть экспортный путь, где
  сырьё минует маскировку? Паттерны всё ещё пробиваемы (но это уже отмечено
  как агрессивно-агрессивно - критикуй, если ОСТАЛСЯ реальный экспорт сырья).
- incarnation-safe id Д4: `event_at` реально различает инкарнации, или есть
  сценарий коллизии/пропажи? Что если два revise в одну секунду (гранулярность
  таймстампа)?
- Валидация вывода Д7: "correction_ids ⊆ входа + не покрыты + >=MIN" -
  закрывает ли злонамеренный валидный кластер полностью, или остаётся
  семантическая дыра (кластер из реальных, но НЕ связанных по сути ids)?
- emitted lifecycle Д8: не-хоронение поправок + показ отклонённых essence -
  сходится ли к покою, или всё же есть петля бесконечных кандидатов? Гонка
  approve с параллельным propose (candidate стал pending, а propose уже
  прочитал ledger без этого покрытия)?
- Ключ (проект,роль) Д2: slug проекта от абсолютного пути - коллизии
  разных путей в один slug? role-валидация при create - не ломает ли
  существующих агентов (роль уже записана в их spec без валидации)?
- Граница Д11: точно ли НЕТ пути записи, параметризованного LLM-выводом/
  ledger-содержимым, выходящего за allowlist? canon.yaml RMW в проекте -
  не портит ли чужую структуру?
- Критерий: verifiable-delivery теперь честно отделён от outcome - но
  достаточен ли delivery-набор, чтобы считать ЭТАП закрытым (или это
  по-прежнему "модель один раз вернула кластер")?

НЕ репортить: стиль; спекулятивные улучшения; отложенные (b)/(c) (критикуй
обоснование, не факт); "добавьте тест" (критикуй достаточность тест-плана).
