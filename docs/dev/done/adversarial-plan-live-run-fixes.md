# Состязательное (adversarial) ревью: фиксы живого прогона агентов (read-only)

Первой строкой отчета напиши: `session id: <id>`.

Ты adversarial-ревьюер. Исходи из того, что это решение СОДЕРЖИТ скрытый
дефект - твоя задача найти его, а не подтвердить корректность. Не одобряй,
ломай уверенность в решении.

## Использование субагентов

По возможности делегируй вспомогательную работу собственным субагентам на
более дешевых моделях: поиск файлов/символов, grep по репо, чтение больших
файлов и выборку фрагментов, сбор фактов. НЕ делегировать дешевым моделям:
финальные вердикты, рассуждения о безопасности/инвариантах, сводное
заключение.

## Контекст

claude-control - оркестрация автономных claude-агентов (bash + systemd
--user + tmux + yq v4 + python3, Linux VM). Сегодня прошел первый живой
прогон mission-агентов (реальные claude-сессии) - он вскрыл 4 дефекта,
которые закрыты четырьмя правками. Их и ревьюим. Часть правок уже
закоммичена (258fa0c..HEAD), финальная (убранный eval) - в рабочем дереве,
смотри git diff HEAD + git log --oneline -6.

## Что ревьюим (4 правки)

1. **Per-agent permissions-сид** - `bin/claude-rc-agent`, cmd_create,
   блок "per-agent permissions" (~строки 250-285). При create mission-агента
   сеется `work/.claude/settings.local.json`: autonomy act/release ->
   `defaultMode=acceptEdits` + allow `["Read(//<agents-dir>/<name>/**)", "Bash"]`
   (голое имя тула = полный Bash); suggest -> defaultMode=default, только
   Read-правило. `.claude/` дописывается в worktree-локальный
   `git rev-parse --git-path info/exclude`, чтобы не попадать в артефакт
   и в дифф приемщика. Контекст-инвариант: bypassPermissions никогда;
   модель угроз v1 - "от ошибок, не от злоумышленника", same-UID гонки
   вне scope.
2. **Чистка stale-scratch реконсилера** - там же, перед `mv "$tmp"`:
   `rm -f $RC_DIR/cache/<name>.flags` (пересозданный одноименный агент
   снова generation=1, старый kick_g1 глушил start-kick).
3. **Убранный eval на LLM-тексте** - `bin/claude-agent-reconciler`,
   run_review_criterion, блок "fencing" (~строки 655-690): раньше
   verdict+summary приемщика извлекались `eval "$(python3 ... json.dumps)"`,
   отчего (а) кириллица уезжала в note/TG литеральными \uXXXX,
   (б) `$(...)` внутри summary исполнился бы шеллом. Теперь rverdict и
   rsummary - две командные подстановки `$(python3 ...)`, summary
   схлопывается в одну строку.
4. **Тестовая обвязка** - `tests/fault/mock-review-claude.sh` (в summary
   мока добавлены кириллица и литеральный `\$(touch /tmp/agent-review-pwned)`)
   и `tests/fault/run-fault-tests.sh` S21 + финальная проверка блока
   (note читаема, зонд не исполнился нигде в S20-S29);
   `tests/test-agent-cli.sh` - новые asserts на сид (57-70).

## Вопросы-направления (не ограничивайся ими)

- Чем ломается permissions-сид: юзкейсы, где acceptEdits+Bash недостаточно
  или опасно; что с сессией, если settings.local.json подхватывается не
  тогда, когда мы думаем; конфликт с handoff-путем (/solo кейс A - там
  сессия оператора адоптируется, а worktree уже содержит наш settings) -
  не меняет ли сид поведение операторской сессии неожиданно?
- git-exclude: переживет ли `git worktree remove`/`prune` + повторный
  create; что если exclude-файл не создался (нестандартный git);
  попадет ли .claude/ в артефакт при `git add -f` агентом?
- rm cache/<name>.flags: какие еще stale-состояния прежней инкарнации
  переживают recreate (alerts-ledger, spool, dedup, tmux-сокеты,
  transcripts, reconciler alerts.jsonl) и чем это стреляет?
- Убранный eval: остались ли пути, где LLM/агентский текст доходит до
  bash-eval или до небезопасной интерполяции (grep eval, printf, sh -c
  по обоим бинарям); корректно ли ведет себя rsummary с бэкслэшами,
  кавычками, очень длинным текстом; что с note дальше по цепочке
  (control-cas --set, alert cmd, tgbot HTML-эскейп)?
- Тесты: ловят ли S21-asserts реальную регрессию (если вернуть eval -
  упадут ли); ложные зеленые.

НЕ репортить (scope exclusions): стиль, нейминг, докстринги; спекулятивные
улучшения; повторы кода без functional impact; "не идиоматично" без
конкретного риска; предложения добавить тесты/доки/телеметрию (это не
атака); все, что уже покрыто принятой моделью угроз v1 (same-UID,
агент с Bash может дотянуться до чужих файлов - осознанно принято).

## Формат

Список атак: по каждой - что атаковал, чем ломается (или почему устояло),
серьезность. Вердикт "проблем нет" допустим ТОЛЬКО с перечнем проверенных
атак и почему они не прошли.

READ-ONLY: только отчет, файлы не менять.
