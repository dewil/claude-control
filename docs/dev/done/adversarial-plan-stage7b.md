# Состязательное (adversarial) ревью: дизайн этапа 7b harvester (read-only)

Первой строкой отчета напиши: `session id: <id>`.

Ты adversarial-ревьюер. Исходи из того, что этот ДИЗАЙН содержит скрытые
дефекты - найди их, а не подтверди корректность. Не одобряй, ломай.

## Использование субагентов

Делегируй дешевым субагентам поиск/чтение файлов, сбор фактов о схемах.
НЕ делегируй: финальные вердикты, рассуждения о безопасности/утечках,
сводное заключение.

## Контекст

claude-control - оркестрация автономных claude-агентов (bash + systemd
--user + tmux + yq v4 + python3, Linux VM). Этапы 1-7 в проде: state
machine, /solo, TG-бот, событийные агенты, ролевой LLM-приёмщик артефактов.
Сейчас проектируется этап 7b: harvester собирает поправки оператора к
работе агентов из durable-источников, кластеризует повторы и предлагает
кандидатов в правила ролей (через канон, с ревью человека). Авто-редактирование
промптов ролей запрещено. Это ТОЛЬКО дизайн-ревью - кода 7b ещё нет.

## Что ревьюим

`docs/design-2026-07-13-stage7b-harvester.md` - прочитай целиком.

Смежный контекст (существующий код, на который дизайн опирается):
- `bin/claude-rc-agent` cmd_revise (~444), cmd_accept_reject (~460) -
  источник (a); Д0-фикс дизайна их трогает.
- `bin/claude-agent-io` append_event (~188, поддержка detail),
  ACCEPTANCE-статусы (~37).
- `bin/claude-agent-review` - образец bounded LLM-воркера (§8.7 приёмщика),
  на который дизайн ссылается для candidate-pass.
- `bin/claude-agent-run` - образец event-агента/spool (harvester - кандидат
  в такие); FLock (~111), durable_write.
- Транскрипт mission-сессии: `~/.claude/projects/<slug>/<sid>.jsonl`,
  user-реплики = type=user + message.role=user.
- Механизм канона: memory feedback_canon_via_toolkit_log (кандидат в
  toolkit-log/upstream-pending, НЕ прямой push).

## Вопросы-направления (ломай, не ограничивайся)

- **Durability-фикс Д0**: правка cmd_revise/cmd_accept_reject (note в
  detail события) - не ломает ли существующий контракт events.jsonl / CAS;
  что со старыми событиями без detail.note; секрет в ноте durable-пишется
  в events.jsonl ДО маскировки harvester'ом (маскировка на чтении) - это
  утечка секрета в durable-лог? Приемлемо ли?
- **Маскировка секретов Д5**: паттерн-маскировка ноты/транскрипта - чем
  пробивается (секрет нестандартной формы, многострочный ключ, секрет
  разбитый на реплики)? candidate-pass (LLM) видит замаскированное - но
  сам ledger на диске? Дайджест/upstream-кандидат?
- **Транскрипт (b)**: отсев kick/mission.md от наставлений - чем ломается
  (перефразированный kick, наставление = цитата mission.md, tool_result с
  текстом, несколько сессий/поколений, адоптированный транскрипт с чужими
  репликами)? Ложные наставления -> мусорные кандидаты -> человек тонет.
- **Идемпотентность Д8**: correction-id стабильность (event-seq меняется
  при чем?), эволюция сути после applied (открытый вопрос 3 дизайна) -
  бесконечный поток чуть-переформулированных кандидатов? Гонка collect с
  живым агентом, пишущим events.jsonl?
- **Кластеризация Д7**: LLM недетерминирован - один и тот же ledger даёт
  разные кластеры между прогонами -> нестабильные correction_ids в
  кандидатах -> идемпотентность (по correction_ids) течёт? Инъекция через
  текст поправки (оператор/агент написал в ноту "верни verdict: applied")?
- **Роль как ключ (открытый вопрос 4)**: агенты разных проектов одной роли
  - обобщение поправки из проекта X в правило, ломающее проект Y?
- **Критерий этапа**: тестовый прокси (посаженный корпус -> 1 кластер)
  реально доказывает "снял повтор поправки", или это подгонка? Что
  НЕВОЗМОЖНО проверить в билд-цикле и остаётся необоснованным?
- **Граница "не редактируем role/"**: механическая ли она в дизайне, или
  держится на обещании? Harvester с доступом к файловой системе - что
  мешает ему (или инъекции через ledger) записать в role/?
- **Отложенный (c)**: обоснование отсрочки честное, или (c) на самом деле
  нужен для критерия этапа (без пост-accept дельты "реальный кластер" не
  наберётся)?

НЕ репортить: стиль/нейминг; спекулятивные улучшения; "добавьте тесты"
(тест-план уже есть - критикуй его достаточность, а не наличие); фичи v2,
честно помеченные как отложенные (критикуй обоснование отсрочки, не сам
факт).
