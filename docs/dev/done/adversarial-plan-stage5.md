## Использование субагентов

Делегируй дешёвым субагентам чтение файлов/сбор фактов о схемах. НЕ делегируй:

## Контекст

claude-control - оркестрация автономных claude-агентов (bash + systemd --user +
tmux + yq v4 + python3, Linux VM). Этапы 0-4,7,7b в проде. Этап 5 -
кросс-машинный takeover: origin-сессия claude на **Mac** переносится в
mission-агент на **VM**. Спайк подтвердил механику (перенос транскрипта + resume
+ relay). Проектируется ПРОТОКОЛ, исключающий двойное владение. Кода этапа 5 ещё
нет - это дизайн-ревью.

## Что ревьюим

`docs/design-2026-07-13-stage5-takeover.md` - прочитай целиком.

Смежный существующий код/дизайн, на который опирается:

- `bin/claude-rc-agent` cmd_create + control.json init (~190-215) - handoff-блок,
  сюда добавляются kind/origin_host/inbox.

## Ключевая идея дизайна (атакуй в первую очередь)

Liveness origin непроверяем на VM -> проверку смерти origin переносим НА MAC
(локальная триада ps/lsof), результат аттестуется в release-маркере {sid,
origin_host, transcript_sha256, released}. VM доверяет маркеру + fencing по
hostname + связке sha256 транскрипта, а не поллингу. VM всё равно держит
локальный дедуп (pgrep/lsof на VM) против двойного импорта.

## Вопросы-направления (ломай, не ограничивайся)

- **Двойное владение**: реально ли push-маркер + Mac-локальная триада + VM-дедуп
  исключают два процесса на одном транскрипте/session_id? Сценарий, где origin на
  Mac ОЖИВАЕТ после выпуска маркера (юзер сделал `claude --continue`/`--resume
  <sid>` на Mac ПОСЛЕ takeover) - VM уже адоптировала, теперь два писателя на
  один sid на разных машинах. Дизайн это ловит или дыра?
- **Связка digest**: `sha256(транскрипт)==marker.transcript_sha256` защищает от
  рассинхрона. Но транскрипт мог быть дописан на Mac МЕЖДУ sha в маркере и scp
  (scp скопировал новую версию) - sha сойдётся с новым или старым? Гонка
  выпуск-маркера / дозапись / scp.
- **Fencing hostname**: `marker.origin_host == control.origin_host` (задан
  оператором при create). origin_host - это чему доверяем? Оператор задаёт хост
  сам -> что мешает опечатке/подмене? В модели "ошибки не злоумышленник" -
  достаточно, или есть ошибочный сценарий (два Mac с одним hostname `macbook.local`)?
- **Идемпотентность/recovery**: push-adopting переиспользует §9.4 recovery. Но
  §9.4 разбирает пару origin/dest в ОДНОМ namespace ($cfg/projects). Здесь H_SRC =
  inbox (другой каталог), H_DST = worktree namespace. Recovery-разбор пары
  inbox/dest корректен? Crash между CAS-adopting и MOVE, потом повторный проход -
  сходится?
- **VM-дедуп до MOVE**: `pgrep -f <sid>` на VM - ловит ли он агентную сессию,
  которая УЖЕ адоптировала этот sid (идемпотентный повтор), и отличает ли от
  постороннего? Ложный wait навсегда?
- **expires_at +30m**: ручной scp дольше окна? Истёк во время большого scp ->
  handoff_expired, а транскрипт долетел следующим проходом - потерян takeover?
- **Mac-хелпер триада на Darwin**: `/proc` нет; `ps -o lstart`/`pgrep -f <sid>`/
  `lsof` - надёжно ли доказывают смерть? starttime-сверка через lstart (секундная
  гранулярность) - переиспользование pid в окне? `pgrep -f <sid>` на Mac - ложно
  пусто, если sid не в argv (сессия по имени, не sid)?
- **Обязательный git push origin'ом**: транскрипт - часть состояния, ветка -
  другая. Если Mac запушил ветку, но VM-worktree агента на другом base -
  агент resume'ит транскрипт, но рабочее дерево не то. Дизайн вяжет транскрипт с
  git-состоянием или это разъезд?
- **Preseed под DEST-cwd**: переиспом claude-agent-session. Namespace-slug DEST
  на VM отличается от origin - resume找 транскрипт по slug DEST (куда MOVE), а
  session_id внутри истории помнит Mac-slug. Resume не форкнет из-за
  несовпадения внутреннего cwd истории?
- **Крах Mac-хелпера между маркером и scp / между scp и create**: маркер выпущен
  (origin помечен released), но агент на VM не создан - висячий inbox, никто не
  импортирует. Уборка? Оператор повторяет - дубль?

НЕ репортить: стиль/нейминг; "добавьте тест" (тест-план есть - критикуй
достаточность); отложенные v2 (VM->Mac и пр.) - критикуй обоснование отсрочки, не
факт.
