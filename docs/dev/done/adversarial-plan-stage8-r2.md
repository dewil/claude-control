## Задача

1. По КАЖДОЙ из 20 своих находок - вердикт **ЗАКРЫТА / ЧАСТИЧНО / НЕ ЗАКРЫТА** с конкретикой, чем именно недостаточно. НЕ верь §9 на слово - проверяй по телу дизайна (§2-§6), совпадает ли заявленное закрытие с реальным механизмом.
2. **НОВЫЕ дефекты**, внесенные переработкой v3 (транзакционная FSM, WAL, resolution-API, per-project rollout_record, durable circuit-breaker, ambient commit_sha).

## Особо проверь (зоны, где переработка могла создать новую дыру)

- **WAL-протокол** (prepare/commit/recovery): детерминированно ли доигрывает/откатывает при crash в ЛЮБОЙ точке (после prepare до rename; после части rename; после rename до state-update; после state до clear). Хватает ли полей журнала (base_sha/target_sha/new_sha/backup_path/phase) для однозначного решения.
- **Ownership desired/applied в state**: двухшаговая запись (desired -> apply -> applied) - нет ли окна, где desired!=applied трактуется неоднозначно; кто чинит; не появилась ли новая гонка двух проходов при durable-полях.
- **resolution_records (keep-local)**: не копятся ли бесконечно (GC); инвалидация при сдвиге upstream_sha - реально ли всплывает как новый conflict; не подавляет ли устаревший record реальное расхождение.
- **per-project rollout_record**: атомарность обновления; хранит ли достаточно, чтобы откатить на per-project предшественника при mixed fleet; граница N последних.
- **durable circuit-breaker / cursor / budget**: singleton-lock реально ли исключает два прохода (crash+timer+marker); latch переживает ли рестарт; учет budget durable ли.
- **identity = ambient commit_sha**: не всплыла ли самоссылочность иначе; доверенный git-транспорт для lock vs CDN только для блобов - выдержана ли граница везде.
- **harvester lifecycle по candidate-id**: замыкается ли (PR-merge -> close by id); миграция двух источников pending - полна ли.
- **fail-closed по schema/min_cli_version**: exit-код 2 (incompat) - не конфликтует ли с остальными; старый CLI против нового lock.
- **mode-поле в схеме**: закрывает ли +x-дрейф; lstat против symlink - нет ли обхода.
- **не-git vault**: versioned backup + journal - выдерживает ли последовательные rollout N->N+1->N+2 и параллельный ручной edit.
