Финальный adversarial-раунд по дизайну (read-only).

Ты adversarial-ревьюер. Дизайн этапа 8 (canon-sync) прошёл 2 раунда: v2 -> 20 находок, v3 -> часть закрыта + новый пласт транзакционных находок. v4 закрывает оставшиеся ДИЗАЙН-дыры и явно выносит транзакционную РЕАЛИЗАЦИЮ в контракт §10. Твоя задача - судить ДИЗАЙН (модель), не реализацию.

## Рамка (важно - согласованная граница дизайн/код)

Транзакционный протокол (точный формат WAL-записи, atomic temp/rename журнала, CAS перед rename, mode в recovery, backup-namespace, синтаксис git cat-file) СОЗНАТЕЛЬНО отложен в §10 как контракт реализации - он доказывается **fault-injection тестами (crash-матрица) в коде**, как этапы 1b/2/4/7 этого проекта, а НЕ прозой. Поэтому:
- НЕ репортить детали формата/реализации §10 как blocker дизайна.
- Репортить по §10 ТОЛЬКО если сам ИНВАРИАНТ логически недостаточен или противоречив (напр. заявленный инвариант не закрывает какую-то kill-точку в принципе, а не "не описан формат байтов").

## Что ревьюим

Дизайн v4: `docs/design-2026-07-14-stage8-canon-sync.md` (прочитай ЦЕЛИКОМ; §9.2 показывает, какие находки закрыты правками П1-П8, какие вынесены в §10; §10 - контракт реализации).

## Контекст системы

claude-control - агенты над claude remote-control на Selectel VM (Linux/systemd; RU-сеть режет raw.githubusercontent). claude-toolkit - канон, снапшотится в .claude/ проектов. Этап 8: детерминированный дельта-скрипт поверх immutable release-descriptor (identity=git commit_sha), LLM только on-demand. Расщепление на intent(человек)/state(дельта)/ledger(harvester). maintenance = детерминированный fleet-reconciler. Harvester (этап 7b, РЕАЛИЗОВАН, bin/claude-agent-harvest) - реальный писатель upstream_pending (кладёт ПУТЬ брифа + candidate-id, lifecycle через ручной mark-applied). Проекты: cactus-adm/sub/doc/order (git), vault (НЕ git), сам claude-control.

## Задача

1. **Дизайн-правки П1-П8 (закрытие Группы 1+3)** - проверь по телу v4, реально ли каждая закрывает находку НА УРОВНЕ МОДЕЛИ:
   - П1 (N7): UNION-классификатор (type-set ∪ state.file_hashes) - реально ли теперь removed-upstream всплывает и файл не сиротеет.
   - П2 (harvester-реальность): дизайн (c) приведён к фактическому harvester (путь брифа + candidate-id, хук mark-applied, один авторитет rollout_record) - нет ли остаточного расхождения с реальным интерфейсом.
   - П3 (N13): release-wide applied_release двигается только по гейту "все пути релиза не-conflict" - закрыта ли грязная история/ложный predecessor.
   - П4 (N11): семантика circuit-breaker (predicate/threshold/latch-to-ring/durable pass-id budget) - определена ли достаточно.
   - П5 (N6): полный host-side клон primary + ретеншн - исполним ли rollback.
   - П6 (N4): standalone не по fleet-managed + CAS-recovery - закрыта ли гонка.
   - П7 (smoke-контракт), П8 (branch applied только после merge; ledger-close по присутствию) - сходится ли FSM.
2. **§10 (контракт реализации)** - достаточны ли ИНВАРИАНТЫ (не формат): покрывают ли CAS-перед-rename, самодостаточность WAL, atomic journal, identity=(blob_sha,mode), backup-по-pass-id все принципиальные kill-точки. Логическая дыра в самом инварианте - репортить; отсутствие деталей формата - НЕ репортить.
3. **Новые ДИЗАЙН-дефекты** от правок v4 (модельные, не реализационные).

## Формат

- Статус П1-П8: закрыта / частично / не закрыта (модельно) + причина.
- Достаточность §10-инвариантов: ок / дыра (какая).
- Новые дизайн-дефекты: серьёзность.
- Итоговый вердикт: **GO** (дизайн готов к коду, транзакц. реализация - через fault-тесты) / **NO-GO** (оставшиеся ДИЗАЙН-blocker).

НЕ репортить: стиль, детали формата §10, реализационные однострочники, предложения тестов (fault-тесты и так в плане кода).
