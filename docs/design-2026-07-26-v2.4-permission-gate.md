# V2.4: гейт подтверждений (permission-request через PreToolUse)

Контракт этапа (SDD). Продолжение V2.1 (пояса прав) и V2.3 (question FSM). Использует их механику целиком: вопрос-подтверждение - это вопрос `kind: permission` в том же FSM.

## Цель

Действие из ask-пояса не выполняется молча и не вешает прогон блокирующим модалом (headless `-p` его не переживает). Хук перехватывает вызов, сам фиксирует запрос подтверждения как вопрос, возвращает deny с инструкцией завершиться. dwl отвечает - runner выдает одноразовый токен ровно на это действие, и следующий прогон его выполняет.

## 1. Генерация хука в settings задачи

`agent-settings.json` (V2.1, генерируется на каждый прогон) дополняется секцией хука, когда в спеке непустой `permissions.ask`:

```json
{
  "permissions": {"allow": [...], "deny": [...]},
  "hooks": {"PreToolUse": [{"matcher": "<инструменты из ask-пояса>",
                            "hooks": [{"type": "command",
                                       "command": "<BIN_DIR>/claude-agent-permit --hook"}]}]}
}
```

- Матчер строится из `permissions.ask`: имена инструментов (`Bash`, `WebFetch`, ...). Тонкая фильтрация по аргументам - внутри хука (см. §2), т.к. matcher матчит инструмент, а не команду.
- `permissions.ask` **никогда** не попадает в `permissions.allow`/`deny` файла settings: allow дал бы молчаливое выполнение, deny - отказ без возможности подтвердить.
- Пустой `ask` -> секция hooks не генерируется вовсе (регресс V2.1 байт-в-байт).

## 2. `claude-agent-permit --hook` (PreToolUse)

Читает событие хука из stdin (JSON: `tool_name`, `tool_input`, ...), каталог агента и ключ конверта - из env (`CLAUDE_AGENT_DIR`, `CLAUDE_AGENT_EVENT_KEY`, как в V2.3).

1. **Соответствие ask-поясу.** Сверяет `(tool_name, tool_input)` с паттернами `permissions.ask` из спеки (§2a). Не подпадает - **нейтральный исход**: stdout пуст, exit 0, решение принимает штатный пояс `allow`/`deny` (аудит V2.4, blocker 1).

   > Первая редакция предписывала здесь `allow` - это была дыра, а не пропуск: матчер PreToolUse ловит инструмент целиком (`Bash`), поэтому явный `allow` от хука накрывал ВСЕ вызовы этого инструмента, включая не перечисленные в `allow` и даже перечисленные в `deny` (hook-level allow сильнее декларативного пояса). При `ask: ["Bash(git push:*)"]` команда `git reset --hard` получала молчаливое разрешение. **Хук возвращает `allow` ровно в одном случае - когда погасил валидный токен (§2.3). Больше нигде.**
2. **Identity действия:** `action_sha256 = sha256(tool_name + "\0" + canonical_json(tool_input))`. Канонизация - `json.dumps(sort_keys=True, ensure_ascii=False, separators=(",",":"))`.
3. **Проверка токена.** Под `approvals/.lock`: если есть `approvals/<action_sha256>.json` со `spent: false` - пометить `spent: true` (durable, под тем же локом) и вернуть `allow`. Погашенный/отсутствующий - дальше.
4. **Создание запроса.** Если открытого вопроса нет - создать вопрос `kind: permission` (тем же кодом, что `claude-agent-ask`, singleton под `questions/.lock`) с полями `tool_request: {tool, input_redacted, action_sha256}` и текстом "разрешить: <redacted-команда>?". Открытый вопрос уже есть - новый не создавать (singleton), просто deny.
5. Вернуть **deny** с сообщением агенту: "запрос подтверждения зафиксирован (qid), заверши прогон - продолжишь после ответа оператора".

Формат ответа хука - `{"hookSpecificOutput": {"hookEventName": "PreToolUse", "permissionDecision": "allow"|"deny", "permissionDecisionReason": "..."}}` на stdout, exit 0.

**Редакция для показа** (`input_redacted`): полный `tool_input` в файл вопроса НЕ пишется - только редактированное представление (существующий `redact()`-подход tgbot: маскировать токеноподобные последовательности, обрезать до 300 символов). Полный ввод не нужен: сверка идет по `action_sha256`, который считается в момент вызова.

## 2a. Синтаксис ask-паттернов: явное подмножество + валидация

Матчер не пытается воспроизвести полную грамматику правил Claude - он реализует **документированное подмножество**, а все, что вне него, отбивается громко, а не молча (аудит V2.4, blocker 2: реализация понимала только `Tool` и хвостовой `*`, а для не-Bash сравнивала паттерн с каноническим JSON - `WebFetch(domain:example.com)` не совпадал НИКОГДА).

**Субъект сравнения** (что именно сопоставляется с аргументом паттерна):

| Инструмент | Субъект |
|---|---|
| `Bash` | `tool_input.command` |
| `WebFetch`, `WebSearch` | `tool_input.url` (или `.query`) |
| `Read`, `Edit`, `Write`, `NotebookEdit` | `tool_input.file_path` |
| прочие | канонический JSON `tool_input` |

**Поддерживаемые формы:**

- `Tool` и `Tool(*)` - любой вызов инструмента.
- `Tool(prefix:*)` и `Tool(prefix*)` - префиксное сравнение с субъектом.
- `Tool(exact)` - точное совпадение с субъектом.
- `WebFetch(domain:host)` / `WebSearch(domain:host)` - хост URL равен `host` либо оканчивается на `.host`.
- `mcp__server` - любой инструмент этого MCP-сервера (`mcp__server__*`); `mcp__server__tool` - конкретный.

**Валидация в `create`** (как whitelist `permission_mode` в V2.1): паттерн, который матчер не умеет вычислить, - ошибка спеки, `exit 2` с перечислением поддерживаемых форм. Отбиваются: не разобравшиеся в `Tool` / `Tool(arg)`; `*` в середине аргумента (`Bash(git * main)`); `domain:` у инструмента, где хоста нет.

**Fail-closed в хуке.** Если у паттерна совпало имя инструмента, но аргумент вычислить нельзя (спеку правили руками мимо валидации) - `deny` с явной причиной, а не "не совпало". Молчаливое несовпадение - именно тот путь, которым blocker 2 включал blocker 1.

## 2b. Отказы - в сторону deny

Хук - гейт безопасности, поэтому любой сбой трактуется как запрет (аудит V2.4, major 4: `except Exception: return []` превращал нечитаемую спеку в пустой ask-пояс, то есть в разрешение):

- `spec.yaml` не читается / `yq` упал или подвис -> `deny` (не пустой список).
- Ошибка файловой системы (lock, запись `spent`, создание `questions/`) -> `deny`.
- `CLAUDE_AGENT_DIR` не задан / не каталог -> `deny`.
- Любое неперехваченное исключение -> `deny` (exit хука с кодом, отличным от 2, PreToolUse НЕ блокирует - падать наружу нельзя).

**Привязка к живому прогону** (major 6, регресс уже закрытого V2.3 major 6): `CLAUDE_AGENT_EVENT_KEY` обязан быть ключом конверта, лежащего сейчас в `inbox/inflight/` этого агента, - иначе `deny` без создания вопроса. Проверка общая с `claude-agent-ask` (единая функция в `_agent_question_io`), поведение и код возврата `ask` не меняются.

Сама проверка идет **с containment** (тот же протокол, что `qid_safe_path` в V2.3): путь резолвится и обязан лежать непосредственно в `inbox/inflight/`. Без этого ключ вида `../../tmp/x` проходил бы проверку при существовании любого чужого `.json` - то есть создавал бы ровно тот осиротевший вопрос, ради которого проверка и заводилась. Форму ключа этот слой не фиксирует: ее задает продюсер конвертов. Кейс - P16c.

**Редакция секретов** (major 5): маскируются не только длинные токеноподобные последовательности, но и значения по ключу - `password`/`passwd`/`pwd`/`secret`/`token`/`api_key`/`access_key`/`authorization`/`bearer` в формах `k=v`, `k: v`, `"k":"v"`, `?k=v`, `Bearer v`. Проверяется на реалистичных строках (`PASSWORD=hunter2`, `Authorization: Bearer abc.def`), а не на искусственной строке из 40 одинаковых символов.

## 3. Выдача токена (runner, answer-прогон)

Единственный создатель токенов - runner, до спавна прогона.

**Решение читается ИЗ ФАЙЛА ВОПРОСА, а не из payload события** (исправление контракта после аудита V2.3, blocker 1). Первая редакция этого документа писалась до того аудита и по инерции повторяла ту же ошибку: `payload.approve` - самозаверение, любой продюсер, знающий `qid`, выдал бы себе разрешение на необратимое действие. Для permission-вопросов цена ошибки выше, чем для обычных.

- Решение записывает доверенный писатель: `claude-agent-answer --qid <qid> --approve | --reject` кладет в файл вопроса `decision: "approve"|"reject"`, `answered_at`, `answered_by` под `questions/.lock`, и только потом ставит адресующее событие в spool. `payload` несет исключительно `question_id`.
- Runner: адресующее событие на permission-вопрос **без записанного `decision`** -> `stale_answer` без спавна (единый стейл-гейт с V2.3: "нет ответа в файле - нечего продолжать", без исключений по видам вопросов).
- `decision == "approve"` -> под `approvals/.lock` durable-запись `approvals/<action_sha256>.json` = `{action_sha256, qid, created_at, spent: false}`. Идемпотентно по `qid`: повторный ответ не создает второй токен и не «разгашивает» уже погашенный.
- **Момент выдачи: сразу после стейл-гейта, ДО построения argv и спавна** (аудит V2.4, blocker 3). Реализация выдавала токен в ok-ветке, то есть уже после выхода модели: прогон, ради которого подтверждение и запрашивалось, стартовал без токена (хук снова отвечал deny, потому что вопрос еще открыт), а токен появлялся, когда использовать его было некому - агент уходил спать, нового события не было. Цикл "ответил - выполнилось" не замыкался вовсе, а тест P4 этого не видел, потому что дергал хук руками мимо прогона.
- Прогон, упавший после выдачи токена, токен не теряет: он остается `spent: false` и достается следующей попытке того же конверта (повторная выдача идемпотентна по `qid`).
- `decision == "reject"` -> токен не создается; в тред пишется `note` "действие отклонено оператором" + причина, вопрос закрывается как обычно (V2.3 §3.5).
- Дальше - обычный answer-прогон V2.3: вопрос закрывается в ok-ветке, промпт получает блок "действие одобрено/отклонено, продолжай".

## 4. Одноразовость и границы

- Токен гасится **атомарно** при первом же успешном матче (§2.3, под локом) - два параллельных одинаковых вызова не пройдут оба.
- Токен привязан к `action_sha256`: другая команда (даже того же инструмента) под него не подойдет; изменившийся `tool_input` -> новый запрос подтверждения.
- Токен не имеет TTL в этом этапе (вопрос и так живет до ответа); уборка погашенных - вместе с задачей (V2.7).
- **Честная рамка (из V2.1 §6):** гейт кооперативен - вложенный вызов внутри разрешенного `Bash` хук не видит. Санитарная граница прежняя: у задачи нет пути наружу, необратимое наружу делает completion-контур (V2.7).

## 5. Регресс-инварианты

- Спека без `permissions.ask` -> settings без hooks, поведение V2.1/V2.3 байт-в-байт.
- V2.3 FSM не меняется: permission-вопрос - обычный вопрос (singleton, заморозка, доминирование над кодом возврата, закрытие в ok-ветке answer-прогона, stale-идемпотентность).
- V2.0/V2.1/V2.2 не затрагиваются; mission-путь не трогаем.

## 6. Тесты

- P1: спека с `ask` -> в agent-settings.json есть hooks.PreToolUse с матчером из ask; спека без `ask` -> секции нет (голден).
- P2: хук на вызов, подпадающий под ask, без токена -> stdout содержит `permissionDecision: deny`, создан вопрос `kind: permission` с `tool_request.action_sha256`, полная команда в файле НЕ хранится (редакция).
- P3 (переписан после аудита): хук на вызов, НЕ подпадающий под ask (но пойманный грубым матчером) -> **нейтральный исход**: в stdout нет `permissionDecision` вообще (в частности нет `allow`), exit 0, вопрос не создан. Отдельный кейс: при `ask: ["Bash(git push:*)"]` вызов `Bash(git reset --hard)` не получает разрешения от хука (blocker 1).
- P4: токен есть и `spent: false` -> `allow` + токен помечен `spent: true`; повторный тот же вызов -> снова deny + новый запрос (одноразовость).
- P5: токен на другую команду того же инструмента -> deny (identity по action_sha256).
- P6: два параллельных вызова хука при одном токене -> ровно один `allow` (атомарный consume под локом).
- P7: `claude-agent-answer --approve` -> токен создан ровно один; повторное адресующее событие -> второго токена нет, `spent` не сбрасывается.
- P8: `claude-agent-answer --reject` -> токена нет, в треде note об отказе, вопрос закрыт.
- P11: адресующее событие с `payload.approve: true` на permission-вопрос **без** записанного доверенным писателем `decision` -> `stale_answer`, токен НЕ создан (подделка разрешения через spool не проходит).
- P9: при уже открытом вопросе новый вызов не создает второго вопроса (singleton V2.3 держит), возвращается deny.
- P10 (регресс): спека без ask - прогон, argv и промпт байт-в-байт как в V2.3.
- P12 (blocker 3, полный цикл через runner): answer-конверт с `decision: approve`; подставной `claude` во время прогона дергает `claude-agent-permit --hook` тем же `tool_input` -> получает `allow` (токен существует ВО ВРЕМЯ прогона, а не после). Контрольный кейс: тот же прогон, но `decision` отсутствует -> `stale_answer`, спавна нет, токена нет.
- P13 (blocker 2): `WebFetch(domain:example.com)` совпадает с вызовом `WebFetch{url: https://example.com/x}` и не совпадает с `https://evil.com/x`; `Edit(/etc/*)` совпадает по `file_path`; `mcp__srv` совпадает с `mcp__srv__tool`.
- P14 (blocker 2, валидация): `create` со спекой `ask: ["Bash(git * main)"]` -> exit 2 с перечислением поддерживаемых форм, задача не создана. Хук на такой паттерн (спеку правили руками) -> `deny`, не тихое несовпадение.
- P15 (major 4): недоступная/битая `spec.yaml` (или `yq`, возвращающий мусор) -> `deny`; отсутствующий `CLAUDE_AGENT_DIR` -> `deny`; ни в одном случае не `allow`.
- P16 (major 6): `--hook` с `CLAUDE_AGENT_EVENT_KEY`, которого нет в `inbox/inflight/` -> `deny`, вопрос НЕ создан (очередь не морозится осиротевшим вопросом). `claude-agent-ask` в том же сценарии ведет себя как раньше (регресс V2.3).
- P17 (major 5): `Bash{command: "curl -H 'Authorization: Bearer abc.def.ghi' https://x/?token=s3cr3t"}` и `PASSWORD=hunter2 ./deploy.sh` -> ни `hunter2`, ни `s3cr3t`, ни `abc.def.ghi` не встречаются ни в файле вопроса, ни в `thread.jsonl`.

## 7. Критерии приемки

- Полный цикл: агент пробует действие из ask-пояса -> deny + карточка-запрос с редактированной командой -> ответ "разрешить" -> следующий прогон выполняет ровно это действие один раз (P2, P4, P7).
- Подтверждение нельзя переиспользовать: ни повторно, ни для другой команды, ни двумя параллельными вызовами (P4, P5, P6).
- Полная команда с возможными секретами не оседает в файле вопроса (P2).
