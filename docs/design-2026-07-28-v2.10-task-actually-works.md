# V2.10: задача, которая реально работает

Этап-следствие раскатки v2 на боевой контур (2026-07-27). Раскатка показала, что путь `/new` с телефона, ради которого делались V2.7a/V2.7b, в бою не проходит ни разу, причем ни один из трех дефектов не ловится ни тестами по контракту, ни состязательным аудитом кода: все они лежат на стыке контура с ЖИВОЙ моделью и с рабочим деревом проекта, а тесты в обоих местах видят мок.

Этап закрывает ровно эти три дефекта. Новой функциональности не добавляет.

## 0. Что именно сломано (факты раскатки)

1. **Штатный шаблон задачи не несет блока `permissions`.** Без него `run_event` уходит на legacy-blacklist `Bash,Edit,Write,NotebookEdit,WebFetch,WebSearch,Task,Agent` (`bin/claude-agent-run`, ветка `else` выбора пояса). Задача с `workspace: worktree` физически не может изменить ни одного файла: первая живая задача честно отчиталась, что писать ей нечем.
2. **Агенту нигде не сообщают о протоколе контура.** Ни `build_prompt`, ни `workspace_frame`, ни шаблон (`role: none`, ролевого промпта нет) не упоминают `claude-agent-done` и `claude-agent-ask`. Заявку о готовности писать некому - значит карточка приемки не возникает, и вся FSM V2.7b недостижима. Проверено дважды: задача заявляла о готовности только тогда, когда команда была вписана в текст самой задачи; на круге доработки (событие = комментарий отказа) она этого уже не делала. Контракт V2.7a этого не оговаривает - то есть пробел проектирования, а не слип реализации.
3. **Подтвержденный урок блокирует интеграцию.** V2.9 пишет зеркало уроков внутрь рабочего дерева проекта (`.claude/rules/lessons.md` по умолчанию), а фаза `integrate` V2.7b справедливо отказывается мержить в вычекаученную ветку с грязным деревом. Вместе: первый же принятый урок останавливает merge всех последующих задач проекта, пока человек не закоммитит файл руками; единственный сигнал - `phase_error` и `attention`.

Общий корень 1 и 2 - **мок в тестах играл за агента**: он сам вызывал `claude-agent-done`, поэтому зеленая суита доказывала машинерию протокола, но не то, что живая модель вообще о нем узнает. Корень 3 - стык двух этапов по общему ресурсу (рабочее дерево), которого не видит ни одна из двух суит.

## 1. Пояс прав штатного шаблона задачи

`examples/task-template.yaml.example` получает `runtime: drain` и блок прав:

```yaml
runtime: drain
permission_mode: default
permissions:
  allow:
    - Read
    - Glob
    - Grep
    - Write
    - Edit
    - "Bash(git status:*)"
    - "Bash(git diff:*)"
    - "Bash(git log:*)"
    - "Bash(git show:*)"
    - "Bash(git add:*)"
    - "Bash(git rm:*)"
    - "Bash(git mv:*)"
    - "Bash(git commit:*)"
    - "Bash(claude-agent-done:*)"
    - "Bash(claude-agent-ask:*)"
  deny: []
  ask: []
```

**`runtime: drain`** - без него задача с телефона держит резидентный юнит, против замысла scale-to-zero V2.0 (там прямо сказано, что иначе RAM-admission упирается в ~3 задачи).

**`ask` пустой - осознанно.** Механика подтверждений (V2.4) работает и здесь: `ask_hook_matcher` сводит `Bash(...)`-шаблоны к матчеру `Bash`, хук дергается на каждый Bash, но для команд, попавших в `allow`, молчит и решение отдает штатному слою прав. То есть `ask: ["Bash"]` технически дал бы агенту любые команды под карточку подтверждения. Так делать НЕ надо: токен подтверждения одноразовый, поэтому повторный `pytest` порождает новую карточку каждый раз - а главный критерий проектирования всей v2 - минимизировать число решений, доходящих до dwl (5-10 карточек в день, иначе защита вырождается в механическое "да"). Человеческий гейт у задачи один и он в конце: карточка приемки.

**Чего в поясе сознательно нет:** сборки, тестов, пакетных менеджеров, сети. Значит агент штатного шаблона умеет читать, править и коммитить, но **не умеет проверить свою работу прогоном тестов**. Это принято как есть: набор команд проверки специфичен для проекта, и угадывать его в общем шаблоне нельзя. Расширение - per-project спекой (`Bash(pytest:*)`, `Bash(npm test:*)` и т.п.), и это единственный правильный канал. Ограничение называется прямо в шапке шаблона, чтобы оператор не искал причину молчаливой неудачи.

**Что несет с собой разрешение git (называется прямо, а не обнаруживается аудитом).** `git` - не примитив, а расширяемый интерпретатор, поэтому:

- шаблон вида `Bash(git commit:*)` - префиксный, поэтому `git -c <опция> commit` под него НЕ подпадает (строка начинается с `git -c`). Это отсекает подстановку произвольных настроек через `-c`, но полагаться на это как на защиту нельзя - при правке пояса легко потерять;
- `git commit` исполняет **хуки репозитория** (`.git/hooks/*`), общие у worktree с основным репозиторием. То есть пояс косвенно разрешает выполнение кода, лежащего в проекте. Это принимается: код проекта - код человека, а задача и так работает внутри его репозитория.

### 1.1 Изоляция записи: путевое ограничение ставит РАНТАЙМ

Первая редакция этого контракта утверждала, что границу держит cwd прогона. **Это неверно, проверено живым прогоном:** с `allow: [Write]` и `--permission-mode default` модель создала файл по абсолютному пути ВНЕ рабочего каталога, и он реально появился на диске. То есть голый `Write` в поясе - это право писать куда угодно, куда может писать пользователь (`~/.ssh/`, `~/.claude/`, соседние проекты). Хуже того, такая запись **не попадает в дифф, который предъявляется человеку на карточке приемки**: гейт показал бы чистый дифф при измененных где угодно файлах.

Поэтому: при генерации `agent-settings.json` рантайм **переписывает голые `Write`/`Edit` в поясе на путевые, привязанные к cwd этого прогона**:

```
Write  ->  Write(//<cwd>/**)
Edit   ->  Edit(//<cwd>/**)
```

Форма с двумя слэшами - не описка: проверено живым прогоном, что именно она матчится как абсолютный путь. Однослэшевая (`Write(/<cwd>/**)`) не сматчилась даже на путь внутри каталога и увела прогон в запрос подтверждения, то есть в отказ для unattended-агента.

Почему в рантайме, а не в шаблоне: путь worktree (`<agent_dir>/work`) существует только на прогоне, в файле-примере его написать нельзя.

Правило применяется ко ВСЕМ рабочим пространствам, включая `none` (там cwd - приватный пустой каталог, и ограничение так же уместно). Уже путевые записи (`Write(...)` с аргументом) рантайм не трогает - автор спеки знал, что делал.

**Что остается открытым и называется явно:** `Read` не ограничивается ничем - агент может прочитать любой файл, доступный пользователю, включая ключи и `.env`. Это **не регресс V2.10**: legacy-blacklist запрещал `Bash,Edit,Write,NotebookEdit,WebFetch,WebSearch,Task,Agent`, но `Read` разрешал всегда, то есть свойство было у каждого агента контура и до этого этапа. Сузить его здесь - значит менять поведение всех агентов, что за пределами этого этапа; зафиксировано как отдельный вопрос.

Поверх всего к `deny` по-прежнему примешивается эшелон доверенных каналов (`trusted_channel_deny_patterns`) - спека задачи не решает, защищены ли ее собственные `questions/`, `reject_comments/`, `lessons.json`, `done.json`.

**Засев.** Шаблон уже кладется `install.sh` (починено раскаткой, кейс S34). Существующий файл в контуре **не перезаписывается** (`copy_example_if_missing`) - у кого шаблон уже есть, пояс не появится сам; это отмечается в заметках релиза, чинить автоматической миграцией нельзя (перезапись затерла бы правки оператора).

## 2. Агент узнает о протоколе контура

Промпт получает **рамку протокола** - что агент вправе сделать с контуром, помимо работы над самой задачей. Место - рядом с `workspace_frame`, то есть в доверенной части промпта ВЫШЕ рамки данных; содержимое события на нее не влияет.

### 2.0 Общий гейт: рамка появляется только там, где команды вообще исполнимы

Про каждую команду контура агенту рассказывают **только если он реально может ее вызвать**. Два условия, оба обязательны:

1. **валидный блок `permissions` в спеке.** Без него рантайм уходит на legacy-blacklist, где `Bash` запрещен категорически, - ни одна команда контура не исполнима в принципе. Ровно это наблюдалось на раскатке: агент честно перебрал формы вызова и отчитался, что команда отбита;
2. **пояс объявляет саму команду.** В `permissions.allow` есть запись, которая либо в точности `Bash`, либо начинается с `Bash(<команда>` для соответствующей команды (`claude-agent-done` / `claude-agent-ask`).

Второе условие - **сверка с тем, что объявил автор спеки, а не сопоставление шаблонов прав Claude Code**: мы читаем декларацию, а не воспроизводим матчер CLI (второй реализации того же заводить нельзя). Для штатного шаблона (§1) и любой вменяемой спеки этого достаточно, а перекос в другую сторону (объявил, но CLI не пустил) - ошибка автора спеки, симметричная любой другой ошибке в поясе.

Практическое следствие - **живые агенты `assist`, `helper`, `fizzbuzz`, `textstats` не затрагиваются вовсе** (блока `permissions` у них нет), и не затрагивается ни один агент, чей пояс не дает команд контура. Последнее проверяется существующим голденом V2.4 `P10` (пояс `["Bash(git commit:*)"]`): он обязан остаться зеленым БЕЗ правок - это и есть доказательство, что правило прицельно, а не размашисто.

Практическое следствие - **живые агенты `assist`, `helper`, `fizzbuzz`, `textstats` не затрагиваются вовсе**: блока `permissions` у них нет, промпт остается байт-в-байт. Это делает регресс-инвариант §2.4 сильнее, чем "workspace: none без questions/": не меняется ни один существующий агент контура.

Проверка условия - тем же выражением, каким `run_event` выбирает пояс (`has_perms and perms_valid`), без второй реализации разбора спеки.

### 2.1 Заявка о готовности

Добавляется при общем гейте §2.0 и `ws != "none"` - то есть ровно у задач с рабочим пространством (`worktree`/`direct`), где заявка вообще имеет смысл (есть что предъявить). Текст - в конец соответствующей ветки `workspace_frame`:

- для `worktree`: заявка предъявляет **коммит**, поэтому вызов идет ПОСЛЕ коммита в свою ветку;
- для `direct`: заявка предъявляет **список измененных файлов**, который контур считает сам.

Формулировка обязана нести три вещи: команду с сигнатурой, момент вызова и **последствие невызова** - именно последнего не хватило живой модели, чтобы догадаться самой.

Текст фиксируется здесь дословно (промпт - и есть контракт этого этапа; тесты пинят подстроки именно отсюда, а не пересказ):

для `worktree`:

```
Протокол контура. Когда работа готова к показу человеку - объяви об этом сам: claude-agent-done --summary "<что сделано, одной фразой>". Зови ПОСЛЕ коммита в свою ветку: предъявляется именно коммит. Без этого вызова работу не увидит никто - карточка приемки строится только из твоей заявки.
```

для `direct`:

```
Протокол контура. Когда работа готова к показу человеку - объяви об этом сам: claude-agent-done --summary "<что сделано, одной фразой>". Предъявляется список измененных файлов, контур считает его сам. Без этого вызова работу не увидит никто - карточка приемки строится только из твоей заявки.
```

### 2.2 Вопрос человеку

Добавляется при общем гейте §2.0 и больше ни при каком. Отдельного признака "событийный агент" не нужно: `build_prompt` вызывается ровно из одного места - `run_event`, - поэтому само попадание в сборку промпта и ЕСТЬ событийный путь.

**Гейт `type == event` рассматривался и отвергнут.** Он был бы не только непроверяемым (mission-агенты до `build_prompt` не доходят вовсе - они идут через tmux/pty, а не через `CLAUDE_BIN`, поэтому кейс "у mission рамки нет" нечем воспроизвести без выдуманного стенда), но и субтильно неверным: `type` в спеке по умолчанию `mission`, так что агент со spool-источником, но без явного `type`, обрабатывался бы как событийный и при этом лишался бы рамки вопроса ни за что.

**Гейт по каталогу `questions/` рассматривался и отвергнут - проверкой, а не рассуждением.** Первая редакция контракта требовала именно его (по аналогии с V2.3 §"Q13") и утверждала, что каталог заводится при создании event-агента. Живая проверка это опровергла: у свежесозданного агента каталога нет вовсе (`claude-rc agent create` кладет только `.lock`, `control.json`, `events.jsonl`, `inbox`, `run`, `spec.yaml`), он создается лениво первым же вопросом (`_agent_question_io.py`, `makedirs` в `create_question`). То есть гейт замыкался сам на себя: нет каталога -> агент не знает, что можно спросить -> не спрашивает -> каталог не появляется. В проде это маскировала гонка: реконсилер на каждом тике зовет `question-reminders`, и та создает каталог под свой лок - но опираться на порядок вызовов внутри чужого прохода нельзя.

 Формулировка несет сигнатуру, необязательные `--options`/`--context`, и главное - **что делать вместо**: не гадать и не отчитываться "сделайте руками" (ровно этим кончались оба живых прогона). Текст дословно:

```
Нужно решение человека - спроси, а не гадай и не отчитывайся "сделайте руками": claude-agent-ask --question "<вопрос>" (можно добавить --options "а|б|в" и --context "..."). Прогон на этом закончится, вопрос уйдет человеку карточкой, его ответ придет тебе следующим событием.
```


### 2.3 Остаточное ограничение

Первая редакция контракта записывала как неустранимое: "рамка не проверяет, доступен ли бинарь поясом, спека без него получит промпт, зовущий к недоступной команде". **Ограничение снято** условием 2 из §2.0 - сверкой с декларацией автора спеки. Повод пересмотреть дал существующий голден V2.4 `P10`: его пояс (`["Bash(git commit:*)"]`) команд контура не дает, и первая редакция правила меняла ему промпт ни за что.

Остаточное - только асимметрия в другую сторону: пояс объявляет `Bash(claude-agent-ask:*)`, но реальный матчер CLI по какой-то причине вызов не пропускает. Это ошибка автора спеки того же класса, что любая другая ошибка в поясе, и лечится тем же способом - прогоном.

### 2.4 Голдены

Правка ломает голдены "промпт байт-в-байт" у агентов, у которых есть валидный блок `permissions` И рабочее пространство и/или `questions/`. Это **осознанное изменение контракта**, а не регресс: такие голдены обновляются вместе с этим этапом. Инвариант сохраняется для всех остальных, и благодаря гейту §2.0 в их число попадают ВСЕ существующие агенты боевого контура: без блока `permissions` промпт байт-в-байт как до V2.10.

## 3. Урок не блокирует интеграцию

Фаза `integrate` перестает считать грязью **ровно один путь** - файл-зеркало уроков этого проекта.

### 3.1 Как считается

`_branch_worktree_status` сейчас: `git status --porcelain` в вычекаученном worktree, грязно = ненулевой код возврата ИЛИ непустой вывод. Меняется на:

1. `git status --porcelain -z --untracked-files=all`. Оба флага обязательны, и каждый - по своей причине, проверенной на живом git:
   - **без `-uall` исключение не сработало бы вовсе**: `--porcelain` схлопывает неотслеживаемый каталог в одну запись, и на боевом контуре наблюдалось `?? .claude/`, а не `?? .claude/rules/lessons.md`. `-uall` разворачивает каталог в файлы; на дефолтную семантику "грязно/чисто" это не влияет (каталог непуст ровно тогда, когда непусты его файлы);
   - **без `-z` сравнение путей ломается на пробелах и не-ASCII**: обычный `--porcelain` отдает такой путь C-экранированным в кавычках (`?? "dir with space/\321\204..."`), и наивное сравнение со строкой пути не сойдется. Пути проектов с пробелами и кириллицей в этом хозяйстве обычны. `-z` разделяет записи нулевым байтом и путь не экранирует.
2. Записи разбираются как `XY <путь>` в NUL-разделенном потоке. **Записи переименования/копирования (`R`, `C`) занимают ДВЕ NUL-записи** (новый путь, затем исходный) - парсер обязан их так и потреблять, иначе исходный путь будет принят за отдельную запись со статусом-мусором.
3. Из потока вычитается запись, чей путь равен пути зеркала уроков проекта ОТНОСИТЕЛЬНО корня этого worktree. Все прочие записи - грязь как раньше.
4. Грязно = ненулевой код возврата ИЛИ непустой остаток.

### 3.2 Откуда берется путь

Только через `project_lessons_path` из `bin/_rc_projects.sh` - единственное место, где разбирается схема реестра (V2.9 §6, аудит блокер 4); второго резолвера не заводим. Имя проекта - `control.json.project_name`.

**Fail-closed.** Резолвер отказал, имени проекта нет, путь не абсолютный или не внутри корня проекта - **исключения нет вовсе**, дерево оценивается как раньше. Отказ резолвера не должен превращаться в "считаем чистым" (это ровно тот класс fail-open, который сплошным проходом вычищали в V2.7b).

### 3.3 Границы послабления

- Исключение применяется и к неотслеживаемому файлу, и к измененному (после первого коммита зеркала новый урок приходит как модификация).
- Исключение НЕ распространяется на каталог зеркала целиком: `.claude/rules/other.md` рядом - обычная грязь.
- Исключение снимает ТОЛЬКО нашу предварительную проверку. Если ветка задачи сама трогает файл уроков, `git merge` откажется сам - и это остается отказом фазы с `phase_error`, как любой другой отказ git.
- `WORKTREE_MULTIPLE` и `WORKTREE_UNKNOWN` по-прежнему безусловно грязные: исключение работает только там, где вывод `git status` реально получен.

## 4. Чего этап НЕ делает

- Не заводит автоматическую приемку по объективной проверке (checkrun/review по диффу) - это отдельный отложенный пункт плана v2, завязанный на решение Р12.
- Не коммитит зеркало уроков за человека и не выносит его из репозитория (рассмотренные и отклоненные альтернативы решения 3).
- Не трогает legacy-агентов: `workspace: none` без `questions/` не меняется ни в поясе, ни в промпте.
- Не чинит накопленный мусор в `~/.claude/.claude.json` (1035 записей от неизолированных суит) - отдельная операция в момент, когда не запущено ни одной сессии.

## 5. Критерии приемки

Тесты пишутся по этому контракту, чистым контекстом, реализацию не читая.

**T1. Шаблон.** `examples/task-template.yaml.example` - валидный YAML после подстановки `{{name}}/{{project}}/{{goal}}`; содержит `runtime: drain`; `permissions.allow` содержит `Write`, `Edit`, `Bash(claude-agent-done:*)`, `Bash(claude-agent-ask:*)`; `ask` пуст. Проверка структурная - по файлу примера, а не по копии в контуре.

**T2. Пояс доезжает.** Агент, созданный из штатного шаблона, при прогоне получает `--settings <agent-settings.json>` (не legacy-blacklist), и в этом файле `permissions.allow` содержит перечисленное, а `deny` - примешанный эшелон доверенных каналов.

**T3. Рамка протокола.** Везде ниже подразумевается валидный блок `permissions`, объявляющий соответствующую команду контура, если не сказано иное. Дополнительно к пунктам ниже обязательны:
- пояс с валидным `permissions`, но БЕЗ `Bash(claude-agent-ask...)` и без голого `Bash` -> рамки вопроса нет; то же для `claude-agent-done` и рамки готовности (по отдельности - рамки независимы);
- голый `Bash` в `allow` -> обе рамки есть;
- существующий голден V2.4 `P10` остается зеленым БЕЗ правок - он и есть регресс-пин прицельности правила.
- `ws=worktree` -> в промпте есть `claude-agent-done --summary`, упоминание "после коммита" и последствие невызова;
- `ws=direct` -> есть та же команда, БЕЗ требования коммита;
- `ws=none` без `questions/` -> промпт байт-в-байт как до этапа (голден);
- рамка вопроса (точный текст §2.2) присутствует у любого агента, прошедшего гейт §2.0, независимо от `workspace` и от наличия каталога `questions/`. Обе комбинации по каталогу обязаны давать ОДИНАКОВЫЙ результат - иначе отвергнутый гейт по каталогу проскочит незамеченным, если в реализации случайно останется проверка;
- **гейт §2.0:** агент БЕЗ блока `permissions`, но с `workspace: worktree` и с каталогом `questions/` -> промпт байт-в-байт как до этапа, ни одного упоминания команд контура. Это кейс живых агентов контура, и он обязан быть отдельным - без него гейт §2.0 не проверяется ничем;
- рамка идет ВЫШЕ блока события (проверяется порядком вхождений в строке промпта).

**T4. Путевое ограничение записи (§1.1).** Проверяется структурно, по сгенерированному `agent-settings.json` - живую отбивку моком не воспроизвести, ее подтверждает ручной прогон, описанный в §1.1:
- голый `Write`/`Edit` в спеке -> в settings уходит `Write(//<cwd>/**)` / `Edit(//<cwd>/**)`, голой записи в `allow` НЕ остается;
- `<cwd>` - реальный каталог этого прогона (для `worktree` - `<agent_dir>/work`);
- уже путевая запись в спеке (`Write(//что-то/**)`) остается как есть;
- правило действует и при `workspace: none`;
- форма ровно с двумя слэшами - однослэшевая не матчится (кейс обязан пинить именно `//`, иначе он зеленый при неработающем ограничении).

**T5. Грязь по зеркалу уроков.**
- в вычекаученном worktree только неотслеживаемый файл уроков (и он появляется внутри неотслеживаемого каталога - случай `?? .claude/`) -> НЕ грязно, `integrate` проходит;
- файл уроков изменен (отслеживаемый) -> НЕ грязно;
- рядом с ним другой неотслеживаемый файл -> ГРЯЗНО;
- проекта нет в реестре / резолвер отказал -> исключения нет, тот же файл делает дерево ГРЯЗНЫМ (fail-closed);
- ветка задачи сама меняет файл уроков и `git merge` отказывает -> отказ фазы с `phase_error`, а не тихий успех.

**T6. Регресс.** Полные суиты `test-agent-task-lifecycle`, `test-agent-lessons`, `test-agent-workspace`, `test-agent-run`, `test-agent-question` зеленые; изменения голденов - только те, что названы в §2.4.
