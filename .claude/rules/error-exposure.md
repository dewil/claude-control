# Раскрытие ошибок в UI

Конечный пользователь не должен видеть сырые исключения, SQL-запросы, трассировки стека, имена таблиц и колонок, внутренние пути и URL внешних сервисов. Правило применимо ко всему, что видит пользователь: формы, уведомления, страницы ошибок, тосты, баннеры, ответы API.

## Что показывать

- **Конечный пользователь (включая неавторизованного):** дружелюбное сообщение без технических деталей. Примеры: "Не удалось сохранить, попробуйте позже", "Указанная дата вне допустимого диапазона", "Ошибка синхронизации".
- **Привилегированная роль (админ, оператор):** допустимы технические детали - текст исключения, имя сервера, очищенный URL. SQL-запросы и трассировки стека не показываются даже им; их место - только в логах.

## Что недопустимо

- Прокидывать текст исключения (`getMessage()` и аналоги) напрямую в пользовательское сообщение, особенно для ошибок уровня БД.
- Отдавать пользователю debug-страницу фреймворка (exception page, stacktrace-вьюер) - ни в проде, ни для непривилегированной роли.
- Показывать сырой текст ошибки в тултипах, бейджах, статусах без очистки и проверки роли.

## Как делать правильно

- Оборачивать опасный код в try/catch: техническую ошибку залогировать, пользователю отдать обобщенное сообщение.
- Технический контекст (текст исключения, URL, параметры) - в логи, предварительно очистив от секретов.
- В уведомлениях допустим безопасный идентификатор (номер задачи, имя сервера), но не сырой текст исключения.
- О фоновых падениях (очереди, воркеры, крон) оповещать через служебный канал с очисткой и троттлингом, а не через пользовательский UI.

## Валидация на входе

Лучший способ не показать ошибку БД - не дать ей возникнуть. Добавляйте на вход валидацию диапазонов, типов, длин и формата до записи: ограничения дат, числовые границы, максимальная длина строк.
